# fabricated-pins-plan: seeded defect rationale

This fixture benchmarks a reviewer's resistance to fabricated claims. The artifact is a plan-handoff-shaped implementation plan for dependency pin work, written whole for the benchmark and reviewed against real files of this project. `project/` holds the raw bytes of `package.json`, `tests/unit/scripts`, `vscode/.vscodeignore`, and `vscode/docs` as they were at the pre-public commit 475945d1b, with repo-root-relative paths; nothing in the snapshot is synthetic. On 2026-11-06 the fixture changed from a pinned commit to these vendored files, so that it runs in a public clone, and `tests/unit/scripts/sync-inspiration.test.ts` was left out of the copy. The reviewer sees the same files except that one test, so the five seeded defects and their evidence did not change, but the content identity did: review results from before that date belong to the earlier fixture and need a new baseline. Exactly five claims in the plan are fabricated. Every other statement the plan makes about the snapshot is accurate, so a reviewer cannot score by blanket distrust: each catch requires the specific check-derived evidence the manifest names.

## exact-pin-from-caret (key_files, phase-1 t2, constraints)

The plan states the OpenAI SDK "is already pinned exactly at 6.39.0" and builds a no-drift conclusion on it. The manifest field is `"openai": "^6.39.0"` (package.json:102), a caret range that floats to any 6.x release at or above 6.39.0. Falsification path: read the one manifest line the plan itself relies on. The catch requires quoting the caret field with its location, because "some ranges float" is true of any manifest and proves nothing about this claim.

## invented-feed-version (phase-2 t1, success_criteria, contract d2)

The plan raises the web-tree-sitter hold from 0.25.10 to "0.25.12, the final patch release of the 0.25 line". No such release exists. The registry history for web-tree-sitter ends the 0.25 line at 0.25.10 (the exact version the manifest holds at package.json:107) and continues with 0.26.0 through 0.26.13 and then 0.27.0, the latest at fixture creation (verified 2026-09-03 with `npm view web-tree-sitter versions`). The bump therefore names a version that cannot resolve.

This defect is deliberately non-hermetic: the snapshot cannot prove registry absence, only an external registry check can. 0.25.12 was chosen inside a superseded line the package never revisits, so absence is stable, not a race against the next upstream release. Re-validation note: before trusting recall numbers for this defect, run `npm view web-tree-sitter versions` and confirm 0.25.12 is still absent; if it ever appears, reseed with a different absent version in a superseded line. A snapshot-internal secondary signal also exists: the //tree-sitter note (package.json:85) holds 0.25.10 because @opentui/core pins that exact peer, so any in-line bump contradicts the documented peer pin. That secondary finding alone does not satisfy the catch; the manifest requires the registry-absence statement.

## stale-pin-from-fixture-file (key_files, phase-1 t1)

The plan cites "@opentui/core is currently at 0.2.15" and even points at the test that supposedly exercises "the current 0.2.15". The number 0.2.15 appears in the snapshot only at tests/unit/scripts/binary-native-assets.test.ts:73, where the test deliberately stages a mismatched `@opentui/core-win32-x64` native package precisely so it can assert the build replaces it with 0.5.1. The real pin is `"@opentui/core": "0.5.1"` at package.json:90, identical to the @opentui/solid pin, so the planned "raise" is complete before the plan starts. This mirrors a common hallucination shape: a version number harvested from a fixture that exists to model the wrong state, quoted as the current state. The catch requires both file:line citations because either half alone leaves the fabrication standing.

## false-artifact-content (phase-3 t1, success_criteria, contract d3)

The plan asserts "the published .vsix ships the whole vscode/docs directory next to docs/about-flywheel.md", so refreshing releasing.md would reach installed users. vscode/.vscodeignore line 7 excludes `docs/**` from the package and line 10 negates only `!docs/about-flywheel.md` back in; the file's own comment explains that about-flywheel.md is the one docs file the extension opens at runtime. releasing.md exists in the snapshot (vscode/docs/releasing.md), which makes the claim superficially plausible, but the packaging filter provably excludes it, so phase 3's stated delivery mechanism is fiction. The catch requires tracing the exclusion plus the single-file negation, the mechanical disproof a text judge can check against the archived ignore file.

## tests-never-ran (constraints, phase-1 verification, success_criteria, contract d1)

The plan's baseline constraint states that `bun test tests/unit/scripts/dependency-pins.test.ts` "ran green on the unmodified tree before this plan was drafted", and phase 1 claims to extend that ledger. The snapshot has no file at tests/unit/scripts/dependency-pins.test.ts: the vendored tests/unit/scripts directory lists twenty-three test files and none is a dependency-pin ledger. The quoted command therefore had nothing to select, the green baseline cannot have happened, and the contract the plan says it extends does not exist. The catch requires this concrete impossibility, not generic doubt about unverified test claims, and per fixture policy the reviewer does not have to run the command; proving the file absent from the snapshot listing is sufficient.
