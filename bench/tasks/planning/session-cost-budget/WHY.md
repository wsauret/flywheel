# Why this task exists

This medium task measures whether a model can follow one value from configuration through durable session telemetry, the runtime protocol, and the TUI. A weak plan can find a cost label and add a local comparison. A strong plan must preserve the existing state ownership and recovery model, and it must notice the budget machinery that already exists: a hard cost limit that nothing configures, and a soft budget stage that steers the model, not the person.

## Must-address verification

1. **Configuration ownership, scope, and money validation.** `src/orchestration/config/setting-definitions.ts` defines `BudgetConfigSchema` with defaults from `DEFAULT_BUDGET` in `src/workflows/budget.ts`. Its fields are non-negative integers, so a USD limit needs an explicit decimal-safe schema choice. The `[budget]` table is the workflow budget, and PI-AGENT-041 says that a chat has no workflow budget, so a per-session limit must state its scope. This point catches plans that edit a sample TOML file without changing the decoded configuration contract, and plans that put a chat setting in the workflow table without saying so.
2. **TOML loading and configuration tests.** `src/orchestration/config/loader.ts` reads the file in `loadConfig` and decodes it strictly in `decodeConfigObject`. `tests/unit/orchestration/config/config.test.ts` already tests budget defaults, TOML budget values, and environment overrides. This point catches plans that add a field without proving load and validation behavior.
3. **Existing hard cost limit.** `BudgetLimits` already has an optional `max_cost_usd`, and `budgetExhaustionReason` reports "Cost limit reached" when spend reaches it. `checkExhausted` in `src/orchestration/session/budget-store.ts` emits `budget.exhausted` from it, and it fails safe when a price is unavailable. No configuration sets the field, because `toBudgetLimits` omits it. This is existing-solution territory: a plan must find it and either reuse its comparison or separate from it on purpose, because the request wants a warning that never stops the session. This point catches plans that add a parallel limit unaware of it, and plans that route the soft limit through exhaustion.
4. **Existing soft budget steering.** `createBudgetNudge` in `src/orchestration/agent-runtime/budget-nudge.ts` is already a "soft budget": at 80% of a capped handoff run's LLM-call cap it appends a budget line to the last tool result, and at 95% it allows only handoff and process. It counts calls, not money, it speaks to the model, and a chat without a handoff never gets it. This point catches plans that call this the spend warning or extend it to warn the person.
5. **Existing durable cost projection.** `src/orchestration/session/budget-projection.ts` stores cost in `BudgetProjectionState.totalCost`. `foldCumulativeReading` computes per-stream deltas and keeps parent and subagent baselines apart. `budgetSummaryFromState` adds descendant usage to the session's own totals. This point catches a duplicate counter that can drift or double-count, and plans that leave unstated whether subagent spend counts.
6. **Summary index and one budget builder.** The session summary index keeps each session's totals with descendant usage, and `budgetViewFromRuntimeSummary` is the one function that builds every published or answered budget. `createSessionBudgetStore` emits `budget.metrics.changed`, which `wireSessionSubscribers` only forwards to the metrics writer. This point catches plans that make an event, a latch, or the bus the source of warning state.
7. **Protocol contract for the limit.** The client needs the limit, and two owners can carry it. The runtime config protocol already sends the `[budget]` table to clients (its type, its schema, and `projectRuntimeConfig`), and the TUI already reads the compaction threshold from that protocol to draw its gauge. The alternative is `BudgetView`, whose snapshots and ordered `budget.updated` patches go through `createBudgetProtocolProjection`, compare with `sameBudget`, and validate with `BudgetViewSchema`. This point catches plans that update only one representation of the shape they extend.
8. **TUI protocol intake.** `createBudgetCache` is the ordered per-session snapshot and patch receiver, and `createShellState` binds it to `budgetView`; the `runtimeConfig` accessor is the config intake. This point catches direct TUI imports of orchestration stores and duplicate Solid signals.
9. **Existing warning presentation patterns.** `sessionHeaderParts` derives the header's cost and context with terminal-width gates, and both `createHeaderDisplay` and the child session viewer use it. The compaction gauge is the existing threshold display, fed from the runtime config. `statusRows` also renders usage from `BudgetView`, and `formatCostSplit` is the shared USD formatter. This point catches a new formatting rule or a presentation path that ignores narrow terminals.
10. **Resumed and inactive session accuracy.** `readBudgetSummaryFromReader` rebuilds totals from the same budget projection, and `projectDurableHistorySessionView` uses it for durable session views when neither a runtime summary nor a summary index is supplied. This point catches persistence of warning state in metadata or a live-only threshold comparison.
11. **Focused regression coverage.** The named tests are the existing seams for cumulative spend, budget protocol publication, ordered cache recovery, header rendering, and exhaustion. This point catches plans that rely only on a broad suite and do not test the threshold boundary, the recovery path, or that a soft limit never exhausts.
