The automatic provider chain work in this tree came back from review with five findings. Can you fix them? Here is what the reviewer wrote:

> 1. The chain decides which provider serves once, when the client is built, and then keeps using it. A long session keeps sending requests to a subscription that ran out after the first request, and it never goes back to a subscription that recovered. Availability has to be checked again for every request (streaming and `complete()` alike). If the whole chain is spent by the time a later request starts, that request should fail with the same typed exhausted-chain error you get today when nothing is available. Please keep `accessProvider` reporting the head of the chain so callers can attribute a request before it starts, keep announcing a different serving provider through `onProviderFailover` before the fallback request goes out, and keep the rule that a quota failure after the attempt produced output propagates instead of starting the fallback.
> 2. ChatGPT availability only looks at the primary rate-limit window. An account whose weekly (secondary) window is at 100% still gets picked. Either window at 100% should count as spent, but ignore a window the backend reports as inactive (zero minutes long) and a window whose reset time has already passed. The skip notice should name the exhausted window's reset, both in the notice id and in the text.
> 3. A quota failure that arrives over the ChatGPT WebSocket fails over the current request, but nothing records it, so the next request picks ChatGPT again. Only the HTTP/SSE error path updates availability. The socket carries the terminal error either as `response.failed` (payload under `response.error`) or as a bare `error` frame (payload on the frame itself); both should mark the window exhausted, with `resets_at` when the frame has one. Frames that are not a terminal quota error must leave availability alone.
> 4. Copilot spend is only committed when a stream finishes normally. If the stream errors, is cancelled, hits the liveness watchdog, or the consumer stops reading after the billed total arrived, the spend is lost and threshold polling keeps choosing exhausted Copilot access. This applies to every adapter that reads Copilot spend. A request must still be billed exactly once, even if commit is reached twice for the same observer.
> 5. Every healthy request resolves its provider notice scope, and the notice reducer returns a new array even when nothing matched. The session patcher reads that as a change, so every healthy request pays for an empty session patch. Resolving something that is not raised should be a no-op.

Do not change which failures trigger failover, and do not add persistence for any of this. Repository-wide `tsc` and lint are already red here because of an unrelated provider addition that is in flight, so do not chase those.
