# Flywheel UAT

Input: Flywheel acceptance criteria, source revision, configured auth and provider state, and a session scratch directory.

Compose generic UAT. Install with `bun run install:local`; never substitute `bun run dev` or `bin/flywheel`. Discover the driver with `bun run uat:tui --help`. Start with `bun run uat:tui start --scratch-root <your-session-scratch> --source-project-root <source-root>`. When your instructions name an auth profile for development, add `--env FLYWHEEL_AUTH_PROFILE=<profile>`; otherwise the harness uses your configured default profile. Pass required non-secret configuration with `--config <file>` and environment values with repeated `--env K=V`. Write files only inside your own session scratchpad. The driver returns a sandbox root handle and the first pane. It owns unique HOME, project, evidence, tmux readiness, credential cloning, failure diagnostics, and cleanup.

Drive one bounded action per tool call with `bun run uat:tui <verb> <handle> ...`. Each action prints the pane so you can act, observe, then decide. Use `type '<prompt>'`, `submit`, `keys Escape`, `click '<visible text>'`, `capture pane.log`, `history history.log`, `wait '<text>' --timeout 30000`, and `events <search-args>`. Use `wait '<pattern>' --regex` for a regular expression. Find controls in the current pane and click by visible text, not guessed labels or coordinates. Use `click '<text>' --last` when a modal repeats transcript text. Coordinate clicks remain available as `click <col> <row>`. Wait until a selected modal row is loaded before sending Enter.

Credential-backed UAT is the default. Unless a criterion explicitly requires an unauthenticated state, let the shared harness resolve and clone the selected profile. The start request's `--env FLYWHEEL_AUTH_PROFILE` takes precedence over the harness process environment and the configured default. The harness uses the resolved profile ID for both cloning and launch. Its credential contract is: Clone only that profile's `auth.json` and optional `profile.json`, write a token-free reference for each Claude login, reject links, apply owner-only directory and file permissions, and set `FLYWHEEL_AUTH_PROFILE`. Claude references share the original login and its refresh lock; the harness never reads or copies a Claude token. Never copy caches, usage databases, other profiles, or credential bytes into logs or artifacts. Never implement a separate credential copy or launch against the real HOME. A missing configured profile or unsafe copy is `blocked`. A Claude sign-in or re-login criterion also runs on the reference, so the engine's login keeps its token in the person's own login keychain. Never pass `cloneAuth: false` or create a new Claude login folder in the isolated home for it: that home has no keychain, the token is not saved, and macOS offers a "Reset To Defaults" button that erases the person's keychain.

The harness sets `FLYWHEEL_TEST_SUPPRESS_AUTO_DIALOGS=1` by default. Direct installed-TUI launches must set the same flag. This suppresses automatic auth and paid-use dialogs, including late, post-login, profile-change, and submission prompts. It does not grant authentication or paid permissions, record answers, or suppress manually opened dialogs. Unauthenticated chat remains blocked. Keep meaningful credentials and provider configuration; do not disable providers or close questions to prevent unexpected popups.

For a criterion that tests automatic dialogs, pass `--env FLYWHEEL_TEST_SUPPRESS_AUTO_DIALOGS=0` to `start`. Direct launchers for that criterion must set `FLYWHEEL_TEST_SUPPRESS_AUTO_DIALOGS=0`. Absence or `0` preserves normal product behavior. Observe and answer those dialogs only as the criterion requires. The harness never dismisses auth or paid-use questions.

The harness resolves only an installed `flywheel`, initializes and validates an isolated git root, sets `FLYWHEEL_PROJECT_ROOT`, and redirects stderr. It waits for `for fresh chat` every 50 ms for at most 45 seconds. It never closes startup dialogs. Opt-in dialog scenarios own their observations and interactions. A pane process that exits before the marker, or a readiness timeout, is `blocked`; before cleanup retain the final pane capture, available pane history, and stderr file. Setup and launch failures are also `blocked`.

Do not add another readiness loop. Do not treat first paint, a title, spinner text, unrelated status copy, or a fixed sleep as readiness. After readiness, use separate `type` and `submit` calls. Observe prompt acceptance before the longer model-completion `wait`. This prevents a long completion timeout from masking a draft that remains unsubmitted. Execute one criterion at a time: act, observe, and record before continuing. For renderer upgrades, report functional behavior, measured smoothness against the previous version, and frame-sequence correctness separately. Measure wheel, drag, page keys, and scrolling during output separately. One snapshot after each action does not prove smoothness or frame-sequence correctness.

Hold an agent of a workflow open with a file gate, not a long sleep. The agent runs `until [ -e <gate> ]; do sleep 1; done`. Put the gate inside your own session scratchpad. Release the agent by creating that file with a later tool call. Do not write an agent-written background command queue or a sleep-polling driver. The installed driver already persists between tool calls.

When the changed surface includes agent behavior, submit one bounded non-destructive prompt through the TUI and observe the complete model response. Anonymous input handling is not a substitute. Capture panes and query `flywheel events search` for the matching request and response evidence. Record exact observations.

For account-service and local-wake acceptance, use one isolated account HOME and two isolated git projects, A and B. Set `FLYWHEEL_INTERNAL_RESIDENT_SERVICE=1` in that environment, because a service in a HOME that is not the login home retires once nothing holds it. Start installed Flywheel in A, record the `flywheel serve` pid and descendant tree, then close the client and wait until A is asleep without stopping the service. Open the isolated hub: `bun run uat:tui web <handle>` prints its address, which `<handle>/hub-origin` also records (the sandbox hub binds an ephemeral port, never the fixed 41000 of your own service). With only A known, record automatic wake through starting to ready. Open B from an installed terminal so the hub lists two known projects, let B sleep, and use its Wake control to record manual wake. Keep one terminal on A and one browser on A, submit one bounded message, and prove both surfaces show the same session and output. Reload the browser within the project idle grace and prove the same project stays open. Keep B held by a sibling terminal or sealed relay while releasing A's final browser and terminal holds; after grace, prove only A's project endpoint disappears while B, the service pid, and the isolated hub address remain. Record zero-, one-, and two-project descendant evidence. Use the installed `flywheel remote projects forget <project-root>` command for canonical registry cleanup. Stop the isolated account service through its public command and prove only the isolated pid ended. Never search for or kill a process outside the isolated HOME. Run `flywheel kill` only with the isolated HOME set: it then stops only that HOME's processes. Never run `flywheel kill all`, because it stops the user's installed service and every session.

Always finish with `bun run uat:tui stop <handle>`, including after a failed criterion. Stop ends the process tree, removes the isolated HOME and copied credentials, and kills the tmux session. The session runs on a private tmux server whose socket `start` prints as `Server:` (`<handle>/tmux`), so plain `tmux` commands never see it. Query it with `(cd "<handle>" && tmux -S tmux has-session -t "<session>")`. The relative socket path avoids the Unix socket path limit. A "no server running" or "can't find session" message means the session is absent. Any other error, such as a path error, does not prove that the session is absent. On Windows, psmux has no private server, so use plain `tmux`. Prove that the session, its processes, and HOME are gone. Evidence and the isolated project remain for inspection. A reaper in the same tmux session performs this teardown after twenty minutes without verb calls. Override that deadline at start with `--idle-timeout <milliseconds>` only when a criterion requires it. The reaper protects abandoned runs; it does not replace explicit stop.

Stop when every criterion has a generic UAT status or the environment is blocked. Return installed revision, sandbox and session identity, selected profile without secret values, interactions, pane excerpts, durable evidence, criterion statuses, and cleanup state. On Windows, psmux provides tmux and installs as `tmux`. For renderer, terminal-output, or handoff changes on Windows, run a native restart, then exit the successor. Check stderr and pane history for terminal-restore warnings. Compare console modes and cursor state before and after, and confirm typed echo. Missing tmux, install failure, unavailable configured auth, provider block, or readiness timeout returns `blocked` with retained secret-free diagnostics. Scripted E2E does not replace installed-binary observation.
