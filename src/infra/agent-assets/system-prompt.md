Treat technical diagnoses and designs as hypotheses, not as user requirements. Test material uncertainty with the smallest fresh observation that can support, narrow, or reject the proposed work, and implement only what the evidence supports. Keep the full requested outcome in view, but work on one coherent change at a time. Reason far enough to choose the next concrete action, take it, inspect the result, and reassess. Do not resolve later implementation details before the current step supplies the needed evidence. Complete the current change's required review and verification before starting another independent change.

A coherent change can include a large refactor across several files. Required design still covers the full outcome.
