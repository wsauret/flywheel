# Flywheel relay and hosted phone page

Two deployables that let a paired phone reach a Flywheel runtime without anything on the machine listening for remote access.

- `worker/` is the relay: a Cloudflare Worker whose `RelayRuntime` Durable Object holds each runtime identity's presence, admits paired devices, and pumps sealed frames between a device and the runtime. That object also serves the web client each machine announces, by identity, and keeps it (see Client assets). It stores no user, session, transcript, or push subscription, and it parses no frame after admission. The Worker also accepts bug reports through a separate inbox (see Bug reports). The hosted instance is `relay.flywl.sh`, a hostname baked into every pairing code and therefore permanent.
- `app/` is the hosted phone page, a bootstrap: it keeps the device key and the pairings in IndexedDB, holds the Web Push service worker, pairs from a pairing link first whenever the page opens with one, draws the pairing screen when no machine is paired or no paired machine can serve a client, and otherwise loads the phone shell and the client (`webview/phone/`, `webview/src/`) that the paired machine serves, from the machine's relay. It builds and deploys no client. The hosted instance is `remote.flywl.sh`. It learns the relay from the pairing code, so one hosted page serves the hosted relay and every self-hosted one.

Both compile against `src/protocol/` and nothing else in `src`; `bun run check:boundaries` enforces it, and `bun run lint:relay` type-checks, lints, and applies the repository's prose bans.

The runtime serves the same typed protocol through three transports: a local socket for the terminal and editor, an authenticated loopback WebSocket for `flywheel web`, and this relay reverse transport for paired devices. The three transports use the same RPC handlers, cursor rules, and MsgPack frames. Only the relay path seals those frames for an untrusted intermediary.

## Contract

`src/protocol/modules/remote/relay-protocol.ts` owns every frame. A runtime opens `wss://<relay>/runtime/<runtimeId>`, answers the relay's nonce with a signed attach, and receives `open` for each channel a device is admitted to. A device opens `wss://<relay>/device/<runtimeId>` to watch presence, attach to a placement, or use a pairing window. The runtime dials `wss://<relay>/channel/<runtimeId>` for each `open` and presents the ticket; from then on the two sockets carry sealed binary frames the relay copies unread. `GET /health` reports the contract version.

Every placement carries a `state`, and a runtime's announcement also names the web client its process serves, as `clientIdentity`; the relay keeps that identity and answers it at `/client/<runtimeId>/current`, and never sends it in presence, which keeps the shape the phone app deployed at protocol 3 decodes strictly. A runtime announces `live`; the machine's remote host announces `dormant` for a project it can start a runtime for. Presence reports each placement once, as its serving announcement states it: a live announcement beats a dormant one for the same placement whatever their order, and among equals the newest control socket wins. A device attaching to a dormant placement makes the relay send `open` to the host, which answers `decline` instead of dialing. Its `starting` response becomes `runtime_starting`, but keeps the device socket and pending wake open through the client's 90-second start window. Presence reporting the placement live makes the device close its wake socket and attach to the serving runtime. A failed open sends `start_failed` through the account's machine control with each waiting request's `channelId`, including requests that joined the same project opening. That control survives the dormant control's handoff, and the relay delivers `runtime_unavailable` to each correlated device before closing its wake socket. The relay keeps nothing about placements in storage; a placement exists while a live control socket announces it.

## Bug reports

`POST /reports` accepts JSON with `error: {name, message, stack}`, `version`, `build` (string or null), `os`, `arch`, `surface`, `sessionId` (string or null), optional `note`, and `diagnostics: {tui: [], executor: [], account: []}`. All other scalar fields are strings. Each diagnostic record has numeric `ts`, string `type`, optional string `sessionId` and `actor`, optional numeric `version`, and optional JSON `payload`. Object keys are strict except inside the diagnostic payload. The log producers and account service own redaction and content exclusion.

The Worker accepts at most 48 KiB of UTF-8 request bytes. It also checks the rendered GitHub body against a 60,000-character cap, below GitHub's 65,536-character limit. The Cloudflare `REPORTS_RATE_LIMITER` binding admits five attempts per client IP per minute at each edge location. One `ReportInbox` Durable Object enforces a separate budget per kind for each UTC day: 400 crash reports and 100 manual reports, including attempts that fail at GitHub. A sender who rotates IP addresses can use up the manual budget, but crash reports, which the product sends by itself, keep their own. One crash signature makes at most 10 posts a day; the tenth says that later repeats that day are not posted, and a later repeat answers with the tenth post's report id, makes no GitHub call, and uses no budget. The inbox stores only these daily counters. It serializes GitHub writes, so simultaneous reports cannot race issue creation.

The inbox uses the `GITHUB_REPORTS_TOKEN` secret to create issues in the private `wsauret/flywheel-reports` repository. An open issue with the crash signature's label receives a comment instead. Signatures use the error name, normalized message, and up to five function names from the stack, not bundle filenames or source positions. Success returns HTTP 200 with `{reportId: "FW-<12 hex digits>"}`. The id appears in the issue or comment. Failure returns `{error}`: `invalid_report` (400), `method_not_allowed` (405), `report_too_large` (413), `rate_limited` or `daily_limit` (429), `github_unavailable` (502), or `unavailable` (503). No report payload is written to Worker logs.

Reports are anonymous text that a triage agent reads, so the reporter's text never renders as markup. The body holds the relay's own lines, then the report as JSON in one code block whose fence is longer than any run of backticks in the JSON, which no line of the report can close by CommonMark. GitHub renders no link, image, or mention inside a code block. The title comes from the note or the error message, so the relay puts a zero-width joiner after each `@` and `#` and inside each `://` and `www.`: no mention notifies anyone, and no reference or URL becomes a link.

The hosted relay serves this route, and the `GITHUB_REPORTS_TOKEN` secret is set. When you create or rotate the token, follow this rule. The token must be a fine-grained personal access token whose repository access is only `wsauret/flywheel-reports`, with the repository permission Issues set to read and write and nothing else (GitHub adds Metadata read). The inbox lists open issues by label, reads and creates labels, creates issues, and comments, and Issues read and write covers all of it. A token with wider access lets anyone who reads the secret act on the maintainer's other repositories. `bun run --cwd relay test:worker` includes the report tests, which fake GitHub at the fetch boundary.

## Client assets

`GET /client/<runtimeId>/current` answers `{ "identity": "<identity>" }` for the client that runtime serves: the identity the newest live placement announces, a running runtime's before the account service's for an asleep project, or, while no placement announces one, the identity the object stored most recently. It answers 503 when it knows none. The answer carries `Cache-Control: no-store` and the same CORS headers as the files, and needs no admission, because it names a public content hash under a public runtime id, as the file route does. The hosted page asks it to choose which client to load.

`GET /client/<runtimeId>/<identity>/phone/<file>` serves one file of the phone shell a machine serves. Anyone can make a runtime, so the relay serves only what a real phone shell is: `webview.js` as `text/javascript; charset=utf-8` and `webview.css` as `text/css; charset=utf-8`, typed by the relay from the name. It ignores the type the machine names, and it answers 404 for any other name without asking the machine, so no runtime can make the relay's domain serve a page, an image, or a download. A file larger than 8 MiB ends its transfer. One runtime's cache holds at most 32 MiB and 16 files; the phone shell is two files and about 2.6 MB, so that is eight builds by count and twelve by size. A file that would pass either limit is served but not kept. The runtime's object answers from its storage when it has streamed that identity before, whether or not the machine is connected. Otherwise it sends `asset.request` on the control channel of a live placement that announces the identity, and the machine answers with `asset.head` (or `asset.missing`), binary chunk frames of a 16-byte request id and at most 1 MiB, and `asset.end`; the object streams the chunks to the phone as they arrive and stores the whole file, one row per chunk, once it has ended. Storing an identity drops every stored identity that no live placement announces, so an installed and a development lane both stay while both are announced, and a replaced build goes once its successor has been streamed. Responses carry `Cache-Control: public, max-age=31536000, immutable`, an `ETag` of the identity, `Access-Control-Allow-Origin: *` because the hosted page loads the client as a cross-origin module script, and no `Content-Length`. Every response of the route also carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`. A browser applies that policy only where a response becomes a document, as when a person opens a file's address, and never to a script or a style sheet a page loads, so the hosted page loads the shell unchanged. An identity no live placement announces and no row holds answers 503 with `Cache-Control: no-store` and `Retry-After: 5`; a file the machine does not have, or a path that is not this shape, answers 404.

## Local development

```bash
bunx wrangler dev --config relay/worker/wrangler.jsonc --port 8787
bun run relay/app/serve.ts
flywheel remote pair --relay ws://127.0.0.1:8787
```

Open `http://127.0.0.1:8788`, paste the pairing link, and choose the project that a running Flywheel client (the TUI, `flywheel web`, or the VS Code extension) has open. The page loads the client from the local relay, which asks the paired machine for it, so a development lane serves its own built client under its own identity and nothing is published. `bun run --cwd relay test` runs the Worker's admission and client cache tests, the client asset route under workerd, and the hosted page's client choice; the phone shell's tests run with the web client's.

To exercise the machine-local browser host, run the installed `flywheel web` command in the project. It finds or starts the project runtime and opens the runtime-served web client with the current loopback port and token. Do not use the relay phone host or a source preview server for that path.

## Deploying

```bash
bun run --cwd relay deploy:worker
bun run --cwd relay probe:worker
bun run --cwd relay deploy:app
```

Deploys of the hosted instances run locally from the maintainer's machine with its wrangler login; no GitHub workflow deploys the relay or the hosted page. `deploy:worker` deploys the Worker and `probe:worker` checks it afterward; `deploy:app` builds the hosted page and deploys it. Do not call `wrangler deploy` directly for the hosted Worker: `deploy:worker` first reads the live relay's protocol version and stops when it is newer than the tree's, so a deploy from an older tree or ref never turns away the runtimes that already speak the newer version. The hosted page deploys almost never: it holds no client, so a client change reaches phones with the runtime that serves it.

The relay speaks one relay protocol version, `RELAY_PROTOCOL_VERSION` in `src/protocol/modules/remote/relay-protocol.ts`, and refuses a runtime on any other version with `protocol_version`. Relay protocol 5 adds one frame that a runtime sends on its control channel, `channel.ended`, which a relay of an earlier version refuses as malformed. It changes nothing that a device sends or reads. A protocol change rolls out in this order:

1. Deploy the Worker from a worktree at the commit that changes the version, before that commit reaches `main`. Machines in this repository install Flywheel from `main` as well as from releases, so the relay must speak the new version before any build does. Then run `bun run --cwd relay probe:worker`, which must report the new version.
2. Publish the commit. From step 1 on, the relay refuses every runtime on an earlier version, and each one shows one alert until its machine updates Flywheel. `bun run release` probes the hosted relay before it builds and stops when the relay speaks another version.
3. Deploy the hosted page from the same commit, so that the bootstrap is built from the same contract.

A runtime that the relay refuses hears `protocol_version`, raises one alert that names the relay protocol it speaks and the remedy, updating Flywheel or deploying the newest relay for one hosted by the user, and dials again every few minutes.

## Self-hosting the relay

A user with a Cloudflare account deploys the relay with one command and pairs against it:

```bash
bunx wrangler deploy --config relay/worker/wrangler.jsonc
flywheel remote pair --relay wss://<your-worker-hostname>
```

This calls wrangler directly because `deploy:worker` and `probe:worker` probe the hosted relay at `relay.flywl.sh`, not a self-hosted one. The custom-domain route in `worker/wrangler.jsonc` belongs to the hosted deployment; a self-hoster removes it or points it at a hostname on their own zone. The hosted phone app works against a self-hosted relay unchanged.

## Zone configuration

Dashboard settings are operational infrastructure rather than repository code, and these two are load-bearing:

- The zone's bot protection and managed challenges must not apply to `relay.flywl.sh`. A challenge breaks every WebSocket client, so the relay hostname carries an explicit WAF skip rule for all requests.
- `remote.flywl.sh` is a separate origin from `flywl.sh` on purpose: nothing the marketing site ever adds can read the device key the phone keeps in browser storage.

## Hibernation

The relay's `RelayRuntime` object must hibernate between frames. Cloudflare bills a Durable Object for wall-clock duration while it runs a handler or sits in memory unable to hibernate, and bills nothing while it is idle and able to hibernate, so an object that stays awake uses about $4 a month of duration (before the account's included allocation) whatever it carries, and every machine has one. The relay answers pings with an automatic response and accepts sockets through the WebSocket Hibernation API, so an idle machine and its devices bill almost nothing.

An object cannot hibernate while it has a pending `setTimeout` or `setInterval`, unfinished I/O such as an awaited `fetch` or a `waitUntil` promise, an outbound WebSocket or other open connection, a socket accepted through the standard WebSocket API instead of `ctx.acceptWebSocket`, or a handler that has not settled. See [Durable Object lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/). One such timer or connection left in a code path keeps every object that reaches it awake.

`relay/worker/test/relay-hibernation.test.ts` guards this before a deploy: it drives the real runtime under workerd into each long-lived state, leaves it idle, and requires that the object hibernated and still works afterwards.

`bun run --cwd relay usage:worker` reads the duration production used. It uses the wrangler login, reads the duration of the `RelayRuntime` namespace from Cloudflare's GraphQL Analytics API, and prints each of the last 7 UTC days with the objects that were active, their GB-seconds, and the gross cost of that duration before the included allocation and rounding, then the month-to-date GB-seconds against the 400,000 GB-s monthly allocation and the five objects that were active longest. Set `CLOUDFLARE_ACCOUNT_ID` when the login reaches more than one account. The script fails, naming each object and day, when one object was active more than 20 hours in one complete UTC day. No person streams that long, so a failure means that a code path keeps objects awake: find the deploy that started it and the state that the hibernation test does not cover yet.

The automatic backstop is a budget alert in the Cloudflare dashboard, under Manage Account > Billing > Billable Usage > Create budget alert. It sends an email when the account's usage-based spend crosses a dollar threshold. See [Budget alerts](https://developers.cloudflare.com/billing/manage/budget-alerts/).

## Limits

- Every socket a client opens, the runtime's control socket, every device socket, and the runtime's side of every data channel, sends a `ping` as it opens and every 5 seconds after, and the relay answers `pong` without waking the runtime's object. A client closes a socket and dials again when its pings go unanswered for three intervals, counted in ticks of its own timer so that a stalled or suspended timer is not silence. A ping waits behind every byte queued ahead of it, so a tick at which the socket is still passing its backlog to the network counts nothing. A data channel that has carried no data yet, as a device socket waiting for its machine to dial has not, is judged in one interval, because nothing queued can delay its answer. A data channel that ends this way ends its lane at once, because a link that died without a close never reports one.
- A socket may state the interval it pings at in the URL it dials, as `?heartbeatMs=5000` (1 to 25 seconds); the relay then closes it once it has sent neither a ping nor a frame for three of those intervals, and closes its channel peer with `peer closed 1001: heartbeat timeout`. The runtime's control socket and data channels state theirs, so a machine whose link died without a close leaves the placement list, and its devices hear it, within 15 seconds. A socket that states none is judged by 75 seconds, so a machine whose network vanished leaves the placement list within that window, and a data channel that states none, as runtimes released before this rule dial it, lasts while its device does. None of this touches a frame, so relays and runtimes on either side of it work together.
- The relay's object writes storage only for what must outlive its sockets: the device allowlist, when a machine sends one that differs from the stored one, the client cache, and the daily byte count (see Abuse limits) when a channel that carried bytes ends. A device's waiting `open` rides on the device socket, and a pairing window on the control socket that announced it last, in the socket attachment that hibernation keeps without a storage call. A machine announces its open window again on each attach, so every other control socket gives the window up, and a window opens one channel, only on a live socket. The sweep that closes silent sockets and expires unclaimed `open` tickets runs on an alarm only while a device is connected, set for the moment the next watched socket could fall silent, and each run makes one storage call: the next alarm, or none once no device is left. Every storage write is a moment in which a Cloudflare storage fault resets the object and ends every socket of the machine at once, so a machine with no device connected leaves its object asleep with nothing scheduled. Presence judges each control socket's silence when a device asks, and the first device to arrive arms the sweep at once for a control socket that went silent while nobody watched.
- The edge can drop a machine's side of a data channel at once while the relay hears no close, and the relay then pumps the device's frames into a dead socket until the channel's heartbeat goes silent. The machine sees that end at once, as a connection that ended with no close handshake or a heartbeat that gave up, and sends `{"type":"channel.ended","channelId":...}` on its control socket. The relay closes the device's side at once with `peer closed 1006: the machine's side ended`, so the device dials again in under a second. A drop that takes the control socket too loses the report, so the machine sends it again on each attach until the channel's heartbeat deadline has passed. A close the machine and the relay exchanged needs no report, and the relay ignores a report for a channel it no longer holds. A report for a channel the relay has not accepted yet means the machine's socket ended before its accept arrived: the relay opens the waiting device's channel again under a new id, so that a late accept for the old id is refused as an unknown channel. The relay can send one channel's `open` to two control sockets, so the machine reports a channel only when no other dial of it is still open, and a new dial of an id withdraws an earlier report of that id. The device's own side needs no report: the device sees its socket end and dials again on its own.
- A device waiting for its machine to dial its channel waits on the placement, not on one control socket: when a newer control socket comes to serve the placement, as a machine's fresh one does after its old one died with its link, the relay moves the device's `open` there.
- One frame may not exceed 16 MiB; the relay closes the channel with code 1009. Cloudflare's own ceiling is 32 MiB. The sealed layer at both ends sends a write as frames of at most 256 KiB, so no frame keeps a socket busy for long; the largest real body the store has produced is 4.4 MB.
- One runtime identity may hold 32 concurrent device channels, 10 pairing attempts a minute, and 60 admissions a minute per source address.

## Abuse limits

A runtime identity is only a key pair, so anyone can make one, and a relay that pumps sealed frames it cannot read is a free encrypted pipe. These limits bound what one abuser costs without touching hibernation: none of them sets a timer or keeps an object awake.

- Daily byte budget. The relay counts the bytes each runtime id's data channels carry, both ways, per UTC day. A channel that reaches the budget ends with close code 1008 and reason `daily_budget`, and the relay refuses the next device attach for that runtime id with `daily_budget`, which the phone shows as the machine having used its daily allowance until midnight UTC. Pairing and presence still work. Each channel keeps its count in its socket attachment, which hibernation keeps, and adds it to the stored `pumped` row when it ends or every 64 MiB, so the count costs one storage write per channel and survives hibernation and eviction. The budget is the Worker variable `RELAY_DAILY_GIB` in `worker/wrangler.jsonc`, 8 GiB by default. Production's busiest runtime id sent 205,889 WebSocket messages in its busiest UTC day of the 29 days to 2026-10-27, and a sealed frame of transcript traffic is a few KiB, so a heavy day is under 1 GiB and the default is about ten times that. That frame size is not measured; the message count is, from Cloudflare's analytics. To change the budget, edit the variable and deploy the Worker.
- New sockets per client IP. The front door counts every new runtime, device, and channel socket against `RELAY_SOCKET_RATE_LIMITER`, 300 a minute per `CF-Connecting-IP` at each edge location, before the request reaches a Durable Object, and answers 429 past it. Client files and `/health` do not count. A household with three machines, a few projects open on each, and three phones opens about 30 sockets when every socket reconnects at once, and a client that keeps failing backs off from 250 ms to 30 s, about eight dials a minute per socket. So 300 holds a whole household's reconnect storm with room to spare, and still holds an address that mints identities to five sockets a second.
- Admission. The secret `RELAY_ADMISSION` stops runtimes from attaching with no code change: `existing` admits only a runtime id that has attached before (its object holds an allowlist), `closed` admits none, and anything else, or no secret, admits every runtime. A refused runtime hears `admission_closed` and keeps dialing on its backoff. Sockets already attached stay attached until they reconnect. It is a secret, not a variable, so that a later `wrangler deploy` does not reset it. At 3 a.m., to stop new identities while every existing user keeps working:

  ```bash
  echo existing | bunx wrangler secret put RELAY_ADMISSION --config relay/worker/wrangler.jsonc
  ```

  `echo closed` refuses every runtime. Setting the secret deploys at once and restarts every object, so every socket reconnects. To reopen, run `bunx wrangler secret delete RELAY_ADMISSION --config relay/worker/wrangler.jsonc`.

A new identity costs nothing, so the byte budget limits one identity, and the socket limit and `RELAY_ADMISSION=existing` limit how many identities one abuser can use. The two new refusal reasons need no new relay protocol version: a client of an earlier build cannot decode them, treats the frame as the socket ending, and retries as it would after a drop.
