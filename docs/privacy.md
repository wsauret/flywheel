# What Flywheel sends over the network

Flywheel runs on your machine. It has no account with us and no product analytics. This page lists every request that Flywheel makes on its own, what each request holds, and how to turn it off.

Flywheel keeps some usage records on your machine: how often you use each slash command, which orders the command menu, and the tokens and spend of each model, which the Usage view shows. Flywheel sends these records only to your own clients, including a paired phone over the end-to-end encrypted connection, and to no analytics service. The remote access relay counts the bytes that it carries in both directions for each machine each day, to apply a daily limit. [Remote access](#remote-access) gives the details.

The Flywheel maintainers run Flywheel's hosted services: the bug report inbox and the remote access relay at `relay.flywl.sh`, and the hosted phone page at `remote.flywl.sh`. To reach the maintainers about a privacy matter, such as a request to delete a bug report, use the private channel in [SECURITY.md](../SECURITY.md): a [GitHub security advisory](https://github.com/wsauret/flywheel/security/advisories/new). Do not open a public issue for a private matter.

Your settings are in `~/.flywheel/flywheel.toml`. In the terminal, open Settings with `/settings`. In the web client, open Settings from the menu.

## Bug reports

A bug report goes to the report address that the build holds. An official release sends it to the Flywheel maintainers. The paragraph "Which builds send reports" below gives the other cases. A report starts in one of two ways.

- **Automatic crash reports.** Flywheel sends no automatic report until you agree. When the terminal crashes, its crash screen asks once whether to send this report and later crash reports automatically. It asks only while Bug reports is on, the build has a report address, Flywheel can read `DO_NOT_TRACK` and it is not set, and you have not answered. If you agree, Flywheel sends the report, and later crash reports and background service faults send without a question. If you do not agree, Flywheel sends nothing. On the phone, the machines screen asks the same question when it crashes while the phone has a project connection. In all other cases, the phone sends nothing and offers to copy the report. The desktop web client and the editor panel never ask, and they send no automatic crash report. A fault of the background service never asks: until you agree, its notice says that no report was sent and offers to copy the report.
- **Reports that you send.** The `/report` command sends a report, with an optional note that you write.

To change your answer, use **Automatic crash reports** in Settings. It shows below **Bug reports** while Bug reports is on. It is the `automatic` key in the `[bug_reports]` section of `~/.flywheel/flywheel.toml`. A sent report shows its report id. A report that was not sent says why and offers to copy the report.

**DO_NOT_TRACK:** When the `DO_NOT_TRACK` environment variable is `1` or `true` in the process that sends a report, Flywheel sends no automatic report, also when you agreed before. `/report` still works. A terminal client reads the variable from its own environment, and then its crash screen does not ask. The background service reads the variable from its own environment and from your login shell. To read the login shell, the service starts an interactive login shell. When that fails, it starts a login shell that is not interactive, which can miss a value that only an interactive shell file, such as `~/.zshrc`, sets. The service keeps the first value that it reads, so a change takes effect when the service starts again. After a read that fails, the service tries again when a project opens. While the service cannot read the login shell, it keeps every automatic report on your machine. The service cannot see a value that you set only for one command, such as `DO_NOT_TRACK=1 flywheel`. For that case, a terminal that starts with `DO_NOT_TRACK` set turns off **Automatic crash reports** if you agreed to them before, and says so. The setting is saved, so the service also stops sending reports of its own faults, also while no terminal is open. You can turn the setting on again in Settings. On Windows, the service reads only its own environment.

**To whom:** An official release sends the report to `https://relay.flywl.sh/reports`, a Cloudflare Worker that the maintainers run. The Worker files the report as an issue in a private GitHub repository that only the maintainers can read. When an open issue already has the same crash signature, the Worker adds the report to that issue as a comment. The Worker uses your IP address to limit how many reports one address can send. The Worker code does not store the address or put it in the report. It stores only daily counters: the number of reports of each kind and, for each crash signature, the number of posts and the id of the latest report. A crash signature is a hash of the error name, the error message with its URLs, paths, ids, memory addresses, and numbers replaced by placeholders, and up to five function names or file locations from the stack. An automatic report has no message, so its signature uses only the name and the stack. The signature is also the label of the issue and a line in its text. After 10 posts of one signature in one day, the Worker posts no more repeats of it that day. A report writes only the counters of its own kind. A counter from an earlier UTC day is ignored, and the next report of that kind replaces it. A report that the Worker does not post because of a limit writes no counter. Cloudflare's [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) are off for this Worker, so Cloudflare keeps no log of each request, with its URL, headers, or your IP address, for the maintainers to read. A separate dev Worker at `relay-dev.flywl.sh` keeps those logs for debugging. Only source runs of Flywheel use it, never a release.

**How long a report is kept:** a report is an issue or a comment in the private repository. It stays there until the maintainers delete it. Nothing deletes reports automatically.

**What every report holds:**

- The kind of report: a crash, or a report you sent with `/report`.
- The Flywheel version, the build id when the build has one, the operating system, and the processor architecture.
- The surface that failed: the terminal, the web client, the phone, the editor, or the background service.
- The id of the chat that was open, when a chat was open. This is a random id, not its title or content. A fault of the background service has no chat id.
- Up to 40 recent warning, failure, and slow-operation records from each of the client, the background service, and the project process. A log that is missing adds no records. A record holds only selected metadata: its time, its type, the name of the component, ids, short codes such as a kind or a signal, counts, sizes, timings, and true or false flags.

**What an automatic crash report adds:** the error name and the stack frames. Each frame holds only a function name when the frame has one, a file name without its folder, and a line and column number. An automatic report holds no error message and no other free text.

**What a report that you send adds:** the note that you write. It holds no error.

**What a report never holds:** Flywheel does not add your conversations, prompts, model replies, tool output, file contents, environment variables, or credentials to a report. The note that you write is the only free text in a report that you send. Flywheel sends the note as you write it, with three changes: it removes the spaces at its start and end, it masks the credential formats that it recognizes, such as API keys and tokens, and it writes the home directory of the machine that runs Flywheel as `~`. Flywheel does not find other secrets, so do not put secrets or private content in the note. When you copy a report that was not sent, the copy also holds the error message and the stack trace, with the same masks, cut to a limited length. The copy goes only where you paste it.

**Which builds send reports:** An official release sends reports to the maintainers. The report address is not part of the program source. The official release machine supplies it when it builds the release. A local build and a source run have no address and send nothing, unless the environment of a source run sets `FLYWHEEL_REPORT_ENDPOINT`. Such a run sends to that address. A fork can build its releases with an address of its own, and those releases send reports to that address, not to the Flywheel maintainers. A build with no address says on its crash screen that no report was sent, and offers to copy the report.

**To turn it off:** turn off **Automatic crash reports** in Settings to stop automatic reports and keep `/report`. Turn off **Bug reports** in Settings to stop every report, automatic or manual. Both are in the Interface group of Settings, in the terminal and in the web client. You can also add `"bug-reports"` to `disabled_modules` in `~/.flywheel/flywheel.toml`.

## Other automatic network traffic

Flywheel makes these requests on its own. None of them sends your conversations or files, except where this list says so.

| Traffic | When | Where it goes | What it sends | How to turn it off |
|---|---|---|---|---|
| Update check | About 10 seconds after the background service starts, then every 30 minutes. Only a build that names a release repository checks: an official release checks `wsauret/flywheel`, and a fork's release checks the fork's repository. A local build or a source run never checks, and its update status says so. | `github.com`, the release files of that repository | A plain download request with no Flywheel identifiers | No setting stops the check. Set `updates.auto_install = false`, or turn off Automatic Updates in Settings, to stop Flywheel from installing what it finds. |
| Release notes | About 10 seconds after the background service starts, when the running release is newer than the release whose notice you last closed. It happens again at each start of the service until you close the notice. Only a build that names a release repository asks. | `api.github.com`, the release list of the same repository | A plain request with no Flywheel identifiers | No setting. Close the notice to stop the request until the next update. |
| Model catalog | When Flywheel first prepares model access for an auth profile. When you open the model picker or the model list of a provider, at most once every 5 minutes for each auth profile. At once when you ask for a refresh, such as Refresh in Providers, and when you select, create, or delete an auth profile. About once an hour in the background while a chat, a workflow, or the default model uses an auth profile. | `models.dev/catalog.json` | A plain request with no Flywheel identifiers | No setting. Flywheel uses a saved or bundled copy when the request fails. |
| Model lists | At the same times as the model catalog, and after you connect or change a provider account. A change of account sends no request to `models.dev`. | Only the model providers that you connected | Your credentials for that provider, as each provider requires. The default `User-Agent` header is `flywheel/<version> (<platform>; <arch>)`, such as `flywheel/0.1.4 (darwin; arm64)`. A GitHub Copilot model list sends the editor and client headers that the Copilot service requires instead. A ChatGPT model list also sends the parameter `client_version`, and your ChatGPT account id in the `ChatGPT-Account-Id` header when Flywheel knows the id. | Disconnect the provider or turn off its module. |
| Model access checks | After a model list, to find which listed models each account can use | Only the model providers that you connected | Your credentials for that provider. A SuperGrok check sends a short request with the fixed text "Reply with only OK.". A Vertex AI check counts the tokens of the fixed text "OK". A Claude engine check asks the engine for a token count and starts no turn. No check holds your conversation. | Disconnect the provider or turn off its module. |
| OpenRouter balance | Before Flywheel sends a request through an OpenRouter API key, at most once every 5 minutes | `openrouter.ai`, the key information endpoint | Your OpenRouter API key | Remove the OpenRouter key or turn off its module. |
| OpenAI prices | When Flywheel lists ChatGPT or OpenAI API models | `developers.openai.com`, the public OpenAI price page | A plain request with no credentials and no Flywheel identifiers | Disconnect ChatGPT and the OpenAI API key, or turn off their modules. |
| Subscription usage | About every 5 minutes while a project is open | Only the subscription providers that you connected | Your credentials for that provider | Turn off **Usage** in Settings. |
| Login refresh | When a stored login expires | The provider that issued the login | The refresh token for that login | Remove the login. |
| Remote access relay | Only after you pair a phone or another device, or while a pairing code is open | `wss://relay.flywl.sh`, or the relay that you chose when you paired | The connection data that [Remote access](#remote-access) lists, and the end-to-end encrypted traffic between your devices | Turn off **Remote access** in Settings, or revoke every paired device. |
| Phone page | When you open `remote.flywl.sh` on a phone | `remote.flywl.sh`, and the relay of each paired machine | Requests for the page and for the web client files, as [Remote access](#remote-access) states | Do not open the page. |
| Phone notifications | When a chat asks you a question that stays unanswered for 1.5 seconds, and a paired phone allowed notifications | The push service of the phone's browser, such as Apple's or Google's | An encrypted message, as [Remote access](#remote-access) states | Turn off **Remote access**, or do not allow notifications on the phone. |

Requests to a model provider carry the prompts and files that you and your agents send to that provider. That traffic goes only to the providers that you connected, under their own privacy terms.

Some traffic happens only when an agent uses a tool. The web search tools send the search query to ChatGPT or Exa. Exa also receives the domain filters and the date limit of a search, and the address of each page that an agent opens, follows, or searches in. Turn off **Web** in Settings to remove these tools. The `models` tool downloads public benchmark scores at most once a day, and sends no data about you. It requests two files from `benchlm.ai` and the public Terminal-Bench leaderboard from `ofhuhcpkvzjlejydnvyd.supabase.co`. MCP servers receive what their tools need, and Flywheel connects only to the servers that you configured.

The bundled Claude engine runs with its own telemetry and automatic updates turned off.

## Remote access

**What the relay can read:** The relay carries the channel traffic between your machine and a paired device. That traffic is sealed end to end, so the relay cannot read your chats. The relay does see the connection setup and routing data that this section lists, and it serves the web client files to the phone. The hosted phone page does not check those files against your machine, so the phone trusts the relay to deliver the client that your machine served.

**What the relay receives:** Your machine connects to the relay only after you pair a device, or while a pairing code is open. When the machine connects, it sends:

- The relay protocol version, its runtime id, its public key, and a signature that proves that it holds the private key. The runtime id is a digest of the public key, so it stays the same until the machine makes a new key. The installed Flywheel and a source run on one machine each have their own key and runtime id.
- The ids of the paired devices.
- For the machine, and for each project that it serves, an id, a name, whether it is live or asleep, the Flywheel version, the protocol version, and the id of the web client build that it serves, when it serves one. The machine's name is its host name, or `dev (<host name>)` for a source run. A project's name is the name of its folder. A project's id is a keyed digest (HMAC-SHA256) of its path, under a key that never leaves your machine, so nobody can use the id to confirm a guessed path.
- While a pairing code is open, an id for the pairing window and the time when it ends.

The relay also sees the setup frames of each connection that are not sealed, such as signed greetings with public keys, device control messages, and the tickets that open channels.

**What the relay keeps:** the ids of the paired devices, a copy of the web client files that your machine serves to your phone, and a byte count for each runtime id. The count is the number of bytes that the channels carried in both directions on the current UTC day. The relay uses it to apply a daily limit. A count from an earlier day is ignored, and the next traffic replaces it. The count holds no content and no record of what you did.

The hosted relay at `relay.flywl.sh` is the default for installed Flywheel. It is the same Cloudflare Worker that receives bug reports, and it keeps no Workers Logs, as [Bug reports](#bug-reports) states. A source run of Flywheel pairs through the dev relay at `relay-dev.flywl.sh` instead, which keeps Cloudflare's Workers Logs: one log for each request, which can hold your IP address, for 3 days on the Workers Free plan and 7 days on the Workers Paid plan. The maintainers can read these logs. A source run that paired before this change keeps the relay that it paired through. To use a relay of your own, pair with `flywheel remote pair --relay <url>`.

**What the phone page requests:** The page loads its own files from `remote.flywl.sh`. For each paired machine, it asks that machine's relay which web client build the machine serves, at an address that holds the machine's runtime id. Then it loads that build's files from the relay. A phone that has no paired machine asks no relay until you pair it.

**What the phone keeps:** The phone page keeps its data in the browser of the phone. A page that you only open stores no data, unless you type a name for the phone. The phone makes its device key when you first try to pair with a code in the correct format, also when that pairing then fails. IndexedDB holds the key, the phone's name, the paired machines, and the project that the phone opened last. localStorage holds the client build that the phone loaded last, with the runtime id and the relay address of its machine. When you add the page to the Home Screen, the start address of the installed app holds a copy of the key and the paired machines after a `#`, so the copy does not go to a server. The installed app writes that copy back into its storage when the storage is empty. The Flywheel client that the phone loads also keeps unsent input and display choices in the browser's storage. When you clear the site data, the browser forgets the pairing, but an installed app can restore it, and the machine still lists the device. To unpair a phone, revoke it in Remote access on the machine.

**Images in chats:** The web client, the phone, and the editor panel show an image from another host as a link to it, so a chat that names an image makes no request to that host. The phone page also lets the browser load images only from the page itself and from data that the client holds.

**Phone notifications:** The push service sees the address of the phone's push subscription and Flywheel's VAPID data: the machine's VAPID public key, and a signed token with the push service's address, an expiry time, and the contact address `https://flywl.sh`. The message itself is encrypted for the phone, so the push service cannot read it. It holds the machine name, the project name, the chat title, a link with the machine, project, and chat ids, and a tag with the chat id and the question id.
