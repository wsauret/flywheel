# Remote Access Product Intent

This document states the current intended experience for reaching a Flywheel runtime from a phone or another browser away from the machine that runs it.

## PI-REMOTE-001: Pairing is the only credential

A user pairs a device, which is a phone, a browser, or a terminal on another machine, by scanning a code that Flywheel shows on the machine, or by opening or pasting the link the code carries. No account, password, or login exists for remote access. A paired device lists the machine's open projects, reads their transcripts as they stream, and sends messages that appear as the next turn.

## PI-REMOTE-002: Nothing on the machine listens

Remote access adds no remotely reachable listener or tunnel to the machine. Flywheel's account service listens only on loopback for local clients and makes outbound relay connections only after a device is paired or a pairing code is showing.

## PI-REMOTE-003: The relay cannot read a conversation

Every frame between a phone and a runtime is sealed end to end. The relay, hosted or self-hosted, learns only that a machine is online, that a paired device is attached, and the names under which a device lists the machine and its projects. A device that was never paired, or whose pairing was revoked, cannot attach even with the relay's cooperation.

## PI-REMOTE-004: Remote reachability is always visible

On every surface, the user can inspect whether the machine is attached to the relay, how many devices are paired, and whether a remote device is attached right now. The terminal keeps its remote indicator; the web header shows no remote badge, and remote readings remain available through Status and Remote access. An attachment the relay no longer holds shows as not attached, with the reason, within 75 seconds, and a machine that lost its network leaves the phone's machine list within the same window. A relay refusing the machine raises a project notification. A device attaching raises none: the attached-device reading remains available, and the device reading a notification would be the one attached. When the machine cannot offer its asleep projects to a phone, the Remote view says so with the reason, and every local surface keeps working.

## PI-REMOTE-005: The phone shows the same client the editor shows

The phone renders the same web client the VS Code extension renders. A feature added to that client appears on both, and the phone differs only by what its host cannot do: open files in an editor, or show a camera for pairing. Connecting a provider, reviewing paid use, managing auth profiles, choosing a model for every role, curating a provider's model list, and reading usage are the client's own sheets, so each of them works on the phone exactly as it does in the editor. Every setting a person can change in the TUI, every action they can take, and every reading the TUI shows is available in the client, except settings that describe the terminal itself, which the client's host owns. On the phone the client owns the screen: a chat sits one screen above the session list, reached and left by a back control, a sideways swipe from anywhere on the screen, and the browser's own back and forward, and the chat's header names the chat and the project the list shows. Every session row and the chat header show whether the session is closed, open and idle, or open and running, with the same rule the terminal's tab spinner uses. Each session row names the session by its short title, shows its longer description under that, and shows the lines the session added, changed, and removed. On a touch screen a row's rename, close, and delete controls stay out of sight until the user swipes the row to the left, and one row shows them at a time; with a pointer they appear on hover.

Phone text selection has generous grab targets. Selection takes priority over swipe navigation and transcript touch scrolling; clearing it restores both.

Back navigation on the phone follows the session hierarchy: a child session returns to its immediate parent, and a top-level session returns to the session list, regardless of visit order.

## PI-REMOTE-006: A user can host their own relay

A user with their own Cloudflare account deploys the relay with one command and pairs against it by passing its URL. The hosted phone app works against that relay unchanged.

## PI-REMOTE-007: A slow phone stays attached

A paired phone that is slow to draw or on a slow link stays attached to its machine while a turn streams. The machine never drops a device for falling behind, and the transcript on the phone catches up in place without reattaching or reloading. Unsupported updates from another runtime version do not interrupt supported views or actions. Diagnostic searches identify skipped unsupported updates and their session when the update names one. A reconnect happens only when the network itself is gone.

## PI-REMOTE-008: Leaving or revisiting a session keeps the reader's place

Switching away from the phone app and back keeps the chat as it was: its scroll position, opened rows, and loaded history stay on screen while the phone reattaches, output that arrived meanwhile appears in place, and reattaching starts the moment the app returns. Switching between open sessions does not reload the app. Switching back to a recently shown session shows it at once, with no loading screen, its draft as the person left it, and output that arrived meanwhile in place. Returning to a session preserves the reader's place and opened rows even when the sessions belong to different runtime versions. Runtime replacement also preserves the selected session, reader's place, and opened rows.

## PI-REMOTE-009: A paired phone can open an asleep known project

When the machine's account service is installed and the machine is awake, a paired phone lists every project this machine has opened from any local or remote surface, shows each as open or asleep, and opens an asleep project with one tap. The row says Flywheel is starting until the project reports open, and says when Flywheel could not open it. A paired device can also create a project on the machine by naming a repository to clone; the machine clones it and then offers it like any project it has opened. It clones only over https or ssh, with the machine's own git credentials and never a prompt, into a new folder named for the repository and numbered when that name is taken, and the clone finishes even if the device leaves. Apart from such a clone, only projects the machine has already opened are offered, and a device never names a path on the machine. A dormant project is forgotten from the flywheel remote projects command, from the phone while it is attached to that machine, from the machine's Remote view, or from the machine's fixed local page, and a project whose directory is gone is forgotten on its own. Opening a forgotten project again on the machine offers it again. The machine stays awake while a phone is using a project it opened, and while that project stays open after the phone leaves, so the phone that comes back finds the machine and its sessions ready, unless the user turns off Keep Awake For Phone. On installed surfaces, the account service's login startup is an explicit action named Process initiation. It reads on or off and says how to change it. A status failure reads unavailable and offers to repair the service; a failed repair says to run `flywheel serve install` on the machine and report a bug if that command also fails. A source build omits Process initiation. A remotely opened project closes after the same idle grace as any other project.

## PI-REMOTE-010: A paired phone opens straight into its session

Opening the app on a phone that has paired and chosen a project shows a Flywheel loading screen, built on the app's own icon with its mark in motion and naming the project and machine it is opening, and then the session itself. Pairing instructions appear only when the phone has no paired machine, or when the relay has reported that the remembered machine is offline or no longer offers the project. Tapping a notification opens the app on the chat or workflow it is about: a chat opens as the chat, and a workflow opens as its full-size card over its chat. Back follows ordinary navigation, so Back from a workflow returns to its chat. Tapping a notification about a question opens its machine and project, shows the chat at its newest output, and shows the question open at the prompt.

## PI-REMOTE-011: The machine's Remote view shows a code or the remote state, never both

While a pairing code is showing, the machine's Remote view carries only the code, its link, and how long it lasts, and returns to the remote state on its own when a phone pairs or the code expires. On installed surfaces, the remote state says whether Process initiation is on or off and how to change it. A status failure reads unavailable and offers to repair the service. A source build omits Process initiation. On starts Flywheel at login, so the fixed local page and a paired phone can wake a project until the person logs out. On Linux, turning Process initiation on also keeps Flywheel running after the person logs out. Where the machine does not allow that, the remote state says that Flywheel stops when the person logs out and names the command that keeps it running. Off does not start Flywheel at login, though a terminal or editor can start it for the current login session. The remote state lists each paired phone under the name the person gave it on the phone before pairing or on the machine afterwards, with whether it is attached right now and when it paired, and lists each known project a phone can open, with paths under the account home shortened to ~. The view repeats no relay reachability reading the prompt frame already shows.

## PI-REMOTE-012: Every surface reaches the same live session

A project appears once and offers all its sessions through one serving runtime. An explicitly requested planned replacement interrupts running work and resumes it on the new runtime, including subagents and workflows, without anyone acting. Planned replacement preserves ongoing work without a visible interruption or user action. A replacement never cuts or reruns a running shell command, foreground or background: the command keeps running, the new runtime takes it over, Stop and the command's timeout still end it, and its result reaches the session that ran it. A foreground shell command that is still running when the replacement takes over continues in the background, as it does when it reaches its foreground time limit. Every other running tool call is interrupted with its turn and runs again when the turn resumes. A question that waits on a person's answer stays open across a planned replacement: the new runtime shows it unanswered, and the turn continues from the person's answer. No running command, turn, subagent, or workflow delays the replacement. A session a person interrupted stays interrupted across the replacement. A replacement never stops a person from sending a message or starting work, asks nothing of them, and shows nothing beyond that move to the background. Every surface then uses the new runtime and retains its session state. Closing a surface does not end work. An unexpected runtime exit leaves interrupted work interrupted until explicit resume.

## PI-REMOTE-013: One account service opens projects on demand

While a person is logged in, a machine with Flywheel installed keeps one lightweight Flywheel service running for that account; on Linux with lingering on, the service also runs while the person is logged out. The service runs without a window: starting it at login or from any surface opens no terminal or console window, and it never depends on one staying open. A project backend is open only while a surface is attached, for up to 20 minutes after a surface that showed sessions leaves so that its return finds them ready, or while work is active, and any surface can open an asleep project through that service.

## PI-REMOTE-014: The phone shows the client of the machine it reaches

The phone shows the client that belongs to the runtime serving the chosen project, loaded from that machine through the relay; nothing publishes a client to the phone app. A newer release on the machine replaces the phone's client without an update of the phone app and without the person doing anything: the page draws again in the same place, with the same session, reading position, and opened rows, and says nothing about the change. A phone that has loaded a machine's client before, or whose relay has served it, still opens while that machine or its projects sleep, and offers wake as PI-REMOTE-009 describes. Pairing a phone for the first time needs the machine awake.

## PI-REMOTE-015: A phone is told when a chat needs it

While notifications are on, a chat that starts waiting on a question shows a notification on each paired phone, on the lock screen too, whatever any phone has open. That is the only moment a phone is notified: a turn that ends, a workflow that pauses, and a run that fails send nothing. A question answered before the notification goes out sends none, and each new question alerts again, also in the same chat. A phone receives notifications from one machine at a time. The installed Flywheel and a source run of Flywheel on the same machine count as that one machine: a phone that gets notifications from one gets them from the other too. Flywheel has no notification setting of its own: allowing notifications on the phone is the only step. While a phone cannot receive notifications, the phone app says why and offers the one next step: adding the app to the Home Screen, a button that asks the phone for permission, the system setting to change when the phone blocks notifications, or moving notifications from another machine to this one. The person can dismiss that offer. The phone remembers the dismissal through relaunches and project switches, and the offer returns only when a chat starts waiting on them while notifications are still off.

## PI-REMOTE-016: A terminal on another machine reaches the runtime through the relay

A person pairs a terminal on another machine with the same code or link that pairs a phone. The paired terminal lists each paired machine's projects as open or asleep, opens or wakes one as a phone does, and shows the same live sessions as every other surface. A terminal opens a project on a paired machine with `--remote`, as an added answer when it asks which directory to open, or from the account home, where a local launch is refused; opening one creates nothing in any local project directory. A terminal on the runtime's own machine attaches locally and never depends on the relay. When the terminal runs an older release than the machine, it updates itself to the machine's release and continues; when it runs a newer release, it says that the machine has not updated yet and attaches once the machine has. A terminal never stops, replaces, or retires a remote machine's runtime.

## PI-REMOTE-017: A version mismatch is explained, not hidden

A machine whose Flywheel is too old or too new for the relay is refused, and the person is told to update Flywheel, or to deploy the newest relay when they host their own. A phone whose app page is too old for the machine's client says so instead of opening the client.

## PI-REMOTE-018: A source run pairs devices on its own

The installed Flywheel and a source run of Flywheel on the same machine pair devices separately, and both can be attached to the relay at once. A paired device lists the installed Flywheel under the machine's name, and the source run as its own machine named dev followed by the machine's name in parentheses, as in `dev (Studio)`. Neither is named after a project. A paired device shows each machine's current name, which it learns whenever that machine is awake, without pairing again.
