# Agent Methods Product Intent

This document states the current intended experience for Flywheel's built-in agent methods and repository-specific extensions.

## PI-AGENT-001: Repository-specific methods are opt-in

Flywheel provides broadly applicable agent methods without imposing one product-development process on every repository. A repository can add stricter domain-specific behavior through project instructions and specialized skills that compose the generic methods. Repositories that do not opt in receive no added ceremony.

## PI-AGENT-002: Broad exploration is bounded and inspectable

Flywheel can inventory and investigate broad multi-system environments through bounded, inspectable work that records coverage, preserves partial results, and produces reviewable documentation.

A survey reports its coverage as the exact number of required targets that it surveyed out of all of them, reports supporting targets separately, and names every target that it did not survey, including each target that failed, was inaccessible, or was excluded. A target that the scope excluded before the survey does not count against coverage. A survey never claims full coverage while a required target is unsurveyed or when it has no required target, and a survey with no targets reports no coverage ratio. An incomplete survey still continues to explicitly partial results.

A workflow join that narrows the results of its agents reports what it dropped and why, beside what it kept. A join that removes duplicates names, for each duplicate, the item of the agent whose entry it kept. A join that keeps the top entries names each entry below the cut. A join that counts votes reports, for each verdict, the valid, refuted, and abstaining votes against its thresholds, and counts an agent that failed as an abstention, so a verdict that no agent supported never passes. A phase over a list can cast several independent votes on each item, each vote in its own agent that no other vote sees, and its join then gives each item one verdict that names the item. Each join also names the agents that failed. The result does not depend on the order in which the agents finished. A workflow can repeat a phase over a list until a round finds nothing new: each agent of a later round sees, as already reported, every entry that the earlier rounds kept or dropped, so it searches for new entries; each round's join drops every entry that an earlier round kept or dropped, names the round that first saw it, and the repeat stops on the first round that keeps nothing, or at its declared number of rounds. A round in which an agent failed never stops the repeat as dry, because that agent did not search.

## PI-AGENT-003: Chat leads requests through delivery

In chat, Flywheel leads change requests from exploration through design, approval, implementation, verification, and review without requiring users to ask for each next part of the work. Feature-feasibility requests enter design, and confirmed bug investigations continue into fix design. Design approval starts delivery immediately. The agents of a workflow run autonomously and do not require approval at each phase.

During implementation, Flywheel follows the original user intent rather than treating the plan as an immutable script. It resolves discoveries, revises implementation choices and phase order, and expands necessary file and repair scope without asking the user for permission or stopping because the plan is wrong or incomplete. It preserves requested outcomes and explicit user prohibitions, verifies the revised work, and reports material deviations for the dispatching agent's final review.

Flywheel agents work incrementally on one coherent change at a time. They use concrete actions and fresh observations to decide each next step while preserving the full requested outcome and required verification.

Flywheel treats diagnoses and technical designs as hypotheses and implements only approaches supported by evidence. Before it shows the user a design, Flywheel spikes it: it tests whether the request is feasible and whether its proposed mechanism works by running disposable prototypes or probes against the real code and systems, and when several viable approaches remain that inspection cannot tell apart, it prototypes and compares them. It says what it is testing while the tests run. Reading code settles what that code does, and the design cites the code for such a claim. Every other claim that the design depends on, such as end-to-end feasibility, runtime behavior, or performance, rests on what a spike observed; the agent's confidence after it reads the code is never that proof. A spike that disproves the approach changes the approach before the user sees a design, and a spike that shows the request is not feasible returns that finding with its evidence instead of a design. The design labels each claim that no spike or code citation supports as untested theory. A claim about an external service, a dependency, or runtime behavior is settled by a cheap throwaway probe against the real system when one is possible, before design and after implementation. User goals, constraints, and explicit decisions remain binding. Evidence can narrow or remove implementation work without weakening those commitments. Additional work must be necessary to satisfy the approved outcome; an independently useful improvement does not expand the task.

An evidence-backed finding that the requested behavior is already satisfied or a reported defect is disproved is a successful no-change outcome, not a demand to invent a fix or run an unrelated test. An investigation that ends without decisive evidence remains unresolved, and Flywheel reports it as unresolved, never as a successful no-change outcome. Flywheel records the rejected premise and fresh decisive evidence. Past observations guide hypotheses but are assumed stale and never substitute for observing the current state. After implementation, it verifies the intended benefit and preserved behavior with the smallest complete fresh proof and stops.

A delegated implementation returns to chat as a first draft of the approved design, not as a finished change. The chat agent that designed the change reads the reported deviations, has the review check the draft against the design so drift is reported beside defects, and then revises the draft against the design it holds until it realizes that design, adding nothing beyond it, and verifies the revised work before it reports completion. Expected drift never returns to the user as a question; only a conflict with the approved design itself returns to the user as a design revision.

When existing user approval does not cover the work, Flywheel presents a complete design and recommended implementation route and lets the user approve, revise, or request an Advisor review first. An Advisor review conditionally approves the unchanged design when the Advisor recommends no material change. A material concern or unavailable review returns the design to the user for a decision. An answer that rejects the approach returns the work to spiking with the user's guidance before Flywheel presents a new design. The design labels its fixed part Design intent, and that label travels with the work into the session checkpoint, specifications, subagent briefs, and reviews, so every agent that touches the work reads the same line between what the user fixed and what an implementer may revise. Revisions require fresh approval only when they exceed the approved scope or introduce a user-owned decision. Before an implementation route starts, chat settles every open question through evidence or the user's exact decision; no open question passes into implementation.

Broad approval covers independent fixes and newly discovered causes within the user's stated scope, including a request to fix all broken lint and tests. Flywheel explains findings and proceeds without per-fix approval prompts. Ordinary bug investigations still require fix-design approval when no such authorization exists. Broad approval does not authorize weaker checks, changed product requirements, or actions with separate consent requirements.

The recommended implementation route states what Flywheel does immediately upon approval. Approval starts that route without another start command from the user. Requests to design, plan, or brainstorm do not stop delivery after planning; only an explicit instruction not to implement makes the task design-only.

Flywheel uses the smallest complete fresh verification of each change. Tests alone are sufficient when they establish correctness; live acceptance testing is used only when needed. Every verification pass observes the current state rather than accepting prior results. Agents stop once that pass's required evidence is complete.

An exhaustive QA campaign requires fresh observations of every surface in every pass, including follow-up passes. Past observations may guide investigation but never count as current QA verification. A fully exercised clean pass may finish with zero fixes.

## PI-AGENT-054: Published code review is a conversation

After Flywheel publishes a change, the user can review its shape by asking the agent about what they see. The chat reply that reports a publication ends with what changed from the approved design during development, with the reason for each change, and the proof that the change works. When Flywheel opens a pull request, its description gives the same two things. The agent answers each review question by explaining the code first. A local objection gets a fix that is verified and published to the same change. An objection to the structure starts a reshape: the agent spikes new structures under the user's guidance, and the reshaped code must pass the proof that the existing change established. Flywheel does not stop before publication to ask for this review.

## PI-AGENT-055: Agents explain their work in conversation

Flywheel agents explain designs, results, and other artifacts in the conversation in plain terms, so the user never has to open an artifact to understand it. When the user challenges a claim, often by saying they are confused and offering a simpler model, the agent restates the user's model, names the exact premise where they differ, and settles that premise with evidence; it neither defends its claim nor concedes by reflex. The challenge ends when the agent shows why its approach is better or gives a justification that the user accepts.

## PI-AGENT-004: Paper-cut campaigns resolve verified pain

When the user invokes `/papercuts`, Flywheel validates every live project paper cut against current evidence, closes records whose pain is resolved, no longer relevant, or not worth fixing, investigates and prioritizes the remaining work, and resolves one root-cause fix at a time until the captured backlog is resolved or the user defers it. Approval can cover the campaign's scope; separate fixes do not require separate approval when that consent already covers them.

## PI-AGENT-005: File editing fits the serving model

Flywheel gives each supported model a file-editing contract and working instructions suited to that model, keeps the same agent behaviors across models, safely repairs unambiguous formatting drift, and refuses ambiguous edits without changing files. An edit that changes nothing reports its files as unchanged, and a change to several files that fails partway keeps the files it already changed.

## PI-AGENT-006: Filesystem tools follow ordinary directory links

Flywheel's filesystem tools follow directory links to inspect and change user-selected files, including installed skills and Flywheel runtime state, while broad traversal does not enter credential-bearing storage.

## PI-AGENT-007: Agents preserve protected memory

Flywheel agents preserve durable memory that users mark as protected. Each memory entry has a protected flag that the user sets or clears by editing the memory file. Protected entries count toward the memory limit. Memory files from earlier releases stay readable and convert to the current format on the next memory change.

## PI-AGENT-008: Completed repository work is published

Flywheel agents verify, commit, and push each repository-changing unit before they start another unit or report completion. When standard gates fail only because of proven unrelated concurrent changes, agents use relevant unit-scoped verification and continue publication.

After verification and review, the working agent delegates publication with the files it changed and a short summary of user intent and implemented design. It does not perform Git analysis or prepare a commit message for the handoff. Ship inspects the selected changes, writes the commit message, commits complete selected files including concurrent edits, and pushes. It does not repeat verification, separate changes by author, select hunks, or create worktrees to isolate edits. Ship publishes only on top of the latest remote work: when the remote holds commits that change a selected file, it stops, and the working agent verifies its change again on the remote tip before it ships.

## PI-AGENT-009: Runtime steering stays private

Flywheel agents keep runtime steering private and give users only task-relevant progress, results, or blockers.

## PI-AGENT-010: Agents preserve session working context

Each conversation has one structured checkpoint with named sections: the design intent, marked when the user approves it; the user's decisions, each with its date, the user's words, and the decision it replaces; the current state; open questions; the next step; the loaded skills that remain relevant; references to recorded history; and working notes. Only the agent that owns the conversation reads and changes its checkpoint through scoped tools, one section at a time. The checkpoint has a size limit, and a change that would exceed it is refused with the reason, never cut short.

Every execution that can compact has the scoped checkpoint tools and instructions to maintain and recover its working context. Executions without this recovery capability do not compact. An attended one stops at the context limit; an unattended one, such as an agent of a workflow, continues its task in a fresh conversation that starts from its brief and its recorded progress. An unattended agent that reaches the context limit before it makes any progress fails with the context-limit reason, because a fresh conversation would start from the same point and reach the limit again.

Agents record the user's design intent in the checkpoint from the moment a request arrives, update it as discussion and experiments change the understood intent, and mark it when the user approves it. Agents record which loaded skills remain relevant to ongoing work and reload those skills when recovering context. Planned automatic and manual compaction gives the agent a bounded opportunity to save current work before reducing context, including when manual compaction starts from idle. During the save opportunity only the checkpoint tools run. When the context overflows before the agent can save, the opening says that the checkpoint may not include the latest work. Compaction then starts fresh conversation context without a generated summary: the fresh context opens with the current checkpoint as a recorded message, with recovery instructions pointing to recorded history. The transcript does not show this opening; it shows the compaction report. A compaction that the person asks for while a chat waits for them runs at once and starts no turn. It keeps how the last turn ended: an idle chat stays idle with no Resume, and an interrupted or crashed chat, or a workflow agent that the person interrupted, shows that turn end again after the compaction and keeps Resume available. Session-backed subagents can retrieve their own earlier history.

A subagent, reviewer, or workflow agent that starts while its parent's design intent is approved receives that design intent and the user's decisions at its start, with their provenance recorded, and cannot change the parent's checkpoint. The agents of one workflow receive the same snapshot, taken when the workflow starts. A child does not receive a design intent that the user has not approved.

The checkpoint remains current when conversation history is rewound. Every earlier version of a checkpoint remains inspectable. Session notes from earlier releases become part of the checkpoint the first time their conversation runs.

With automatic compaction enabled, Flywheel saves a checkpoint for large idle chats before the estimated expiry of a prompt cache whose provider stated a minimum lifetime for it, resets context, and remains idle. It does not automatically wake interrupted chats or chats waiting on background work. Users can disable idle compaction in Settings. An idle checkpoint that fails or is interrupted preserves the conversation context.

## PI-AGENT-011: Memory preserves selective cross-session understanding

Flywheel uses limited memory selectively for durable cross-session understanding of the user and their working context. Session working notes remain separate. Agents maintain shared repository guidance in applicable project instructions rather than duplicating it in memory.

## PI-AGENT-012: Experiment loops start from an approved charter

When the user invokes `/experiment design`, Flywheel leads a charter design conversation that settles the objective and its decomposition into a primary metric, secondary metrics, hard gates, anti-gaming rules, files in scope, protected and sealed paths, the measure and checks commands, the baseline procedure, and the search strategy, and proves that the measure command emits the declared metrics before the charter is complete. The transcript presents the charter conversation after an `/experiment design` divider and shows the supplied goal as the first user message after that divider. The charter and its scripts are repository files the user owns. An experiment loop cannot start without a complete charter whose primary metric has been produced at least once.

## PI-AGENT-013: Experiment loops measure, keep, and revert autonomously

When the user starts an experiment loop, Flywheel runs it without further prompts: the agent proposes one change at a time, Flywheel measures each attempt by running the charter's measure command itself, runs the charter's checks after a passing measurement, records every run, commits an attempt only when the agent keeps it after passing checks, and reverts the working tree for every discarded, crashed, or checks-failed attempt. The charter's protected paths cannot be written and its sealed paths cannot be read by the loop. Results, including the best kept result and a noise-floor confidence score, are visible live in every client. The loop continues until the user stops it, the charter's iteration cap is reached, or repeated failures stall it, and it never destroys work outside its own dedicated working tree.

## PI-AGENT-014: Kept experiments become reviewable branches

When the person runs `/experiment finalize`, Flywheel groups kept experiments into independent changesets that share no files, proposes the grouping for approval, and creates one clean branch per group from the merge base so each can be reviewed and merged on its own.

## PI-AGENT-015: Workflows resume across compatible method changes

Flywheel resumes a workflow when its graph and execution contracts remain compatible, records changed method content used after resume, and stops before work starts when a structural change makes the recorded run incompatible. The stopped workflow then says that its definition changed and names each changed part once. It says how to continue the work: start a new workflow, or, when the project defines every changed part, restore those parts and press Resume. Resume continues the workflow when its definition matches again, and otherwise names the parts that still differ.

## PI-AGENT-016: Cross-model tool-history continuity

When a conversation continues with a model that has a different tool contract, Flywheel presents prior tool work through the current model's tool surface without changing the durable transcript or teaching an incompatible tool invocation.

## PI-AGENT-017: Shell changes remain inspectable

When an agent declares that a shell command mutates files, Flywheel captures the changes in the work tree that contains the command's working directory and shows that call the way a file tool shows its change: a file the command created reads as a write, and a file it changed or deleted reads as an edit. This presentation starts from the moment the declaration arrives and is backed by the same mutation evidence in session history. While the command's input arrives and while it runs, its row reads as an edit with one line that says a bash command is running, without the command text. When it settles without landed changes, its row reads as the ordinary shell command it ran. The changes never include concurrent work by other agents. When a file changed elsewhere while the command ran, Flywheel rebases the command's change onto the current file; only the regions both sides changed are marked as conflicts, and the agent is told to resolve them. A command declared as mutating captures only its changes to file contents. Git commands that change the repository run without that declaration; inside a mutating command they are refused with a message that says so. A write to another work tree of the same repository is refused with a message that tells the agent to set the command's working directory to that tree. When Flywheel cannot capture a mutating command's changes, it runs the command in place, as if it were not declared as mutating, and says that its changes were not captured. A process that a mutating command starts can end when the command ends: on Windows, and on Linux hosts where the guard runs the command in its own process namespace, it always does. A long-lived process, such as a server or a watcher, belongs in a separate command that is not declared as mutating, and plain commands keep their processes as before. Shell commands that are not declared as mutating run without extra repository work, and Flywheel does not show their changes as file writes or edits or include them in the session's changes.

Every agent's shell refuses recognized writes and deletes outside the project, the `.flywheel` folders, and the project's registered worktrees, except device sinks. The working directory does not widen that allowance. A target that Flywheel cannot place is refused too. An unknown working directory does not refuse a write whose literal path Flywheel can place inside the allowance. The refusal first says that the command was blocked because it is not a safe command. It stops the whole command, names the target and reason, and directs the agent to the project or scratchpad. An unplaceable target requires a literal path. The refusal ends by telling the agent not to rephrase the command to reach the same target. This is a guard against mistakes, not a sandbox for arbitrary programs. A read-only agent, such as the explorer or a reviewer, may write only in its scratchpad or to device sinks; other recognized writes and deletes are refused.

## PI-AGENT-018: Stalled operations retry at a smaller scope

When a model response stalls while composing an oversized operation, Flywheel redirects its retry to produce a smaller sequential batch instead of retrying the operation unchanged. Normal batching resumes after that model response completes.

## PI-AGENT-019: Subagent budget caps are reported honestly

When a subagent stops at its turn budget, the parent agent and every client see a partial result, distinct from a completed or failed run, so unfinished work is never read as done. The turn budget counts every model request of the dispatch, including requests of runs that recovery started again after a provider fault; only an explicit Resume starts a new budget.

## PI-AGENT-020: A child can be interrupted and resumed

A running subagent can be interrupted from any surface. Interrupting stops it at once, keeps every result it has already committed, and shows on its card that it is interrupted and whether a person, its parent agent, or the runtime interrupted it. A runtime abort pauses the subagent rather than marking it failed. A subagent that waits on background work is still working and never ends because of inactivity.

Every subagent that has not completed successfully admits explicit Resume, including partial, failed, stopped, and canceled work. Resume continues the child's saved conversation without a new assignment or rerunning recorded tool calls. A failed attempt to resume says what prevents it. A parent agent can interrupt and resume its own subagent. A resumed workflow or subagent counts as its parent's running background work, the same as a newly launched one, however it was resumed. A child resumes only under its parent's live host. A chat parent attaches idle without starting its turn; when no parent host can run the child, Resume says to resume the parent first. The parent agent never resumes work that a person interrupted or stopped: work a person interrupted continues only when a person resumes it or sends it a message, and work a person stopped continues only when a person resumes it. Resume availability does not recommend resuming or authorize automatic continuation. Stop ends the current work and remains distinct from interrupting; only an explicit continuation starts it again.

## PI-AGENT-021: Global skill edits need no separate permission

Interactive agents create and change managed global skills without a separate approval. The applied tool result identifies the skill as global.

## PI-AGENT-022: Bash analysis does not depend on warmup

Flywheel makes command analysis ready when an agent uses Bash or exec. Recognized writes and deletes with outside or unplaceable targets are refused before the command runs. If analysis cannot load or complete, including exhaustion of its work or nesting budget, that failure does not block the command, regardless of agent role or available file-editing tools, and Flywheel reports the analysis failure without repeated warning noise. Restrictions on commands that Flywheel can identify independently still apply.

## PI-AGENT-023: Output-limit recovery is bounded

When a model response reaches its output limit, Flywheel makes only bounded automatic continuations. If these also reach the limit, Flywheel preserves the received output, stops automatic requests, and shows an actionable output-limit error. A successful response or a new user request starts a fresh recovery allowance.

## PI-AGENT-024: Only the root chat asks the person

An agent sends another session a message only to ask a question that blocks its work and that its own tools cannot answer, to answer a question that it received, to revise the instructions of its own child or workflow, to deliver what its person asked it to send, or to tell another root chat once that a check fails in a file that the other chat owns. One message carries everything that the recipient needs. Its first sentence says what the message is about and what the sender needs. The message uses complete sentences and has no greeting or preamble. A question gets one answer, and an answer ends the exchange. Agents do not send acknowledgements, thanks, confirmations, status or progress reports, promises of a later update, requests to be told later, "are you done?" checks, or copies of a message to a session that already has it. An agent that cannot answer a question from its own child asks its parent in its own words. When the result of a message says that the recipient holds it or refuses it, the agent does not send the message again or a reminder, and it continues its own work. A refused wait is the one exception: the agent can send the message again without the wait. A session that does not reply has not agreed to anything, and the sender does not act as if it had. The person sees every message in the transcript, so an agent does not quote or restate one to its person unless the person asks. When a message needs a decision from the person, the agent asks only that question, in its own words. Delegated results return through the result handoff, and the completion notice of a child tells its parent when the child finishes.

A recipient replies only when a message asks it a question or its sender waits for the reply. Flywheel requires no reply to a message from another session. Each session message names the sender's relation: parent, child, sibling, or other. Siblings have the same parent. A peer is neither the recipient's parent nor its child.

A message from the parent applies to the recipient's current work at once. A message to an agent session, including the parent's reply, reaches that session only and adds nothing to the workflow request. The chat that launched the workflow is the agent's direct parent. No workflow relays its questions.

A message to a workflow from its launching parent adds direction to the whole workflow or its addressed items or named agents. Each reached later agent reads the original request and the additions for its address in order. An addition is direction unless it states a change to Design intent. A later addition applies where it conflicts with an earlier addition of the same tier. Recording an addition never replaces the original request, restarts an agent, or starts work on its own.

A message from the person applies to the agent or address that receives it. A peer message carries no authority. The recipient weighs it as information unless attached words show that the person requested it, and finishes its current work first. A peer message to a workflow goes to one reader and becomes no direction. Peers are not workers: an agent never asks a session other than its own child to fix, commit, publish, or revert files. Only a parent and its own child can wait on each other for a reply. A workflow takes no reply wait.

Root chats do separate work for the same person. A root chat starts an exchange with another root chat only when its person asks it to, when it needs a fact that only that chat has, or when a check fails in a file that the other chat owns. When a check fails in a file that another root chat owns, it tells that chat once, with the file, the check, and the exact error, asks nothing in that message, and then treats failures in that file as not its own. It does not wait for the fix or ask whether the fix landed. It answers a question from another root chat about commits, publication, integration, or progress once from its own state, because each chat publishes its own work. It answers its person's question about progress from its own state and tools. When its person writes to it, it stops any exchange with another root chat that the person did not ask for.

Only a chat that no other session started asks the person questions. A subagent or an agent of a workflow that meets a choice it cannot make from the design and the evidence, such as a conflict with the approved design or with an explicit prohibition of the person, or that a missing external prerequisite stops from every viable next action, sends its parent a message that states the evidence and waits for the reply. It resolves expected drift itself (PI-AGENT-003). The parent answers from what it knows, or it asks the person and then replies. When no parent can answer now, as in an unattended run with no connected parent chat, the child learns this at once. It then continues on its own judgment, and its result states the assumptions that it made.

A child never stops as blocked. A child run ends as completed, as stopped or canceled, or as failed only when the run itself breaks: a fault that only a person can clear, or a fault that repeats on fresh attempts with no progress between them. A subagent that reaches its turn budget ends as partial (PI-AGENT-019). Interrupted work has not ended and can resume.

## PI-AGENT-025: Managed-work waits receive timed assessments

Every agent wait on managed work, including shell commands, subagents, and workflows, has a finite duration. An explicit wait includes commands launched in the background, including servers and services. The agent sets that duration from its estimate of the remaining work, especially for subagents and workflows. Without an estimate, the wait lasts at most four minutes. Completion or expiry wakes the agent without terminating the work. A wait that a restart or planned replacement cuts keeps its deadline: it continues on the new runtime without waking the agent, and the downtime counts toward its duration. When an assessment finds nothing to act on, the agent waits again without writing to the transcript. The agent can read the progress of its own child without waking it or sending it a message: for a workflow, the current phase, how many agents are done out of the planned total, and which agents completed; for a subagent, its state, operations, and tokens. The agent can also message its child, interrupt it, resume it, or call wait again with a fresh estimate. A parent names agents in `targets` to interrupt or resume only them. A child that its parent or the runtime interrupted is not active work, so no wait parks on it, and a parent that interrupts the child it waits on stops waiting at once. A child that a person interrupted stays the parent's active work: the parent is not told, and its waits park on the child and expire as any wait does. Each wait expires once; no assessment repeats without another wait call. Questions addressed to the person and interrupted sessions do not resume through a wait expiry.

## PI-AGENT-026: A child hands off only after its background work ends

A subagent or an agent of a workflow hands off only when none of its background work remains: no command that it started still runs, including a server or another service, and no subagent or workflow that it started still runs or has a result that has not reached it. It waits for work that finishes on its own, and it stops a service before it hands off. A handoff that it tries earlier is refused, and the refusal names each item of work.

## PI-AGENT-027: A message to a workflow reaches the agents that it is for

A message to a workflow ID from its launching parent is direction. Without an address it reaches the whole workflow: every running and later agent, including every item whose agents have not started. Each agent reads it once. With an address, it reaches only the named items or agents, including later agents that the address covers. A workflow is orchestration, not a session, and takes no reply wait. An accepted untargeted peer message remains information for one agent, not direction for the workflow.

A message to an agent session ID reaches only that session. This includes the parent's reply to its question. It adds nothing to the workflow request. When a message changes the agent's work, the agent records the change in its handoff, quoting the instruction and what it replaces. Later agents receive that record through their declared outputs; direct input does not become an addendum for siblings.

The parent names item keys or named-agent IDs in message_session targets, using the phase-grouped keys that process status shows. Only the launching parent can use these targets. The person's agent-view composer addresses the agent's item or named agent through the workflow. Its placeholder names that address. A running addressed agent reads the message after its current action. An interrupted or paused addressed agent reads it when it continues, also after a restart.

An item whose agents have not started reads its addressed message in its first phase. Its agent in each later phase of the stream reads it too. Another item never reads it before the join, which receives it with their results. Each addressed agent whose work changes records that change in its handoff. A person's addressed message continues interrupted work. The parent's does so unless a person made the latest interrupt.

A finished item, unknown or ambiguous key, or invalid agent ID refuses the whole message before storage. The refusal lists valid keys, their items or agents, and their states. A key reused by a finished list names the unfinished item. The same words sent to two different addresses are two messages. Neither a whole-workflow nor an addressed workflow target takes a reply wait.

## PI-AGENT-028: Saved definitions load without a restart

A skill or persona definition saved into the project's or account's Flywheel definition folders is available to running sessions without a restart. A definition that an agent saves with its managing tool is available to that agent's next request; other running sessions see it when Flywheel observes the folder change. While a saved change to a loaded definition cannot load, sessions keep using the definitions that loaded last. A new definition that cannot load is skipped, and other saved changes still load. A skill or persona definition written for another agent tool loads when its only problem is an unquoted colon in a frontmatter value. Workflow files do not enter this catalog. A chat agent can launch one by path.

## PI-AGENT-029: A workflow is phases of agents that run briefs

A workflow lists phases that run in order. A phase runs one agent, a few named agents at the same time, or one agent for each item of a list. A phase can follow the phase before it item by item, so each item moves through both phases at its own pace. A phase can run only when an earlier phase completed, or only when a field of its output is not empty. A repeat runs its own phases in rounds: while a field of one of its phases is not empty, at most a stated number of rounds, or once for each item of a list, one item after another. A workflow file can state its attempt limit, at most 4096; without one, its limit is its worst-case attempt count, which also must not pass 4096. A launch that queues more attempts than its limit is refused, and the refusal names both counts. A file can also cap how many agents run at one time.

A workflow path value uses the machine's path syntax and can be absolute or relative to the workflow's working directory. A declared output path must exist unless its field permits a file that does not exist yet. The handoff preserves the path as supplied, including a path to a scratch artifact outside the working directory.

An empty `reads` declaration requests no additional outputs and does not prevent a workflow from starting. A transient artifact can state `supersedes: []`, but it cannot supersede another artifact.

Phase and agent names can contain lowercase letters, digits, hyphens, and underscores, starting with a letter or digit, and each name is used once in a workflow. Command words are valid names. Dots separate references, not parts of a name. These names retain their exact spelling in model assignments and saved runs; global workflow and skill names keep their own rules.

A chat agent writes a workflow file and gives each agent its brief: its instructions and declared output. The file holds each brief inline. Another agent can reuse a brief from the same file. A brief can compose installed skills but cannot run a skill as its task. Flywheel ships no briefs. An agent whose brief declares no output hands its summary to the next phase. A handoff records each command that it cites with the command, the directory that the call named, and the exit code of the call that ran, and names each file that changed in the agent's session after that call, never values that the agent typed. A citation of a call that did not run, or a repeated citation, is left out, and the agent is told. A handoff is refused for its citations only when too few real citations remain, and the refusal names the calls that the agent can cite. An agent's task is its own brief and the inputs that it declares. Context is lean by default: an agent receives the request that started the workflow as background, not as its task, and keeps its work within the scope that the request states, the output of the phase just before it, and the durable outputs, and no other earlier output unless the agent names that output in its `reads`. Only the agent that names an output receives it, labeled with the id that it names, and a workflow that names an output that cannot finish before the agent starts is refused before it runs. The next agent also sees the file changes that each earlier agent it builds on made itself, including the changes of each subagent or workflow that the agent launched, apart from changes by other agents, other items, other sessions, or the person, and sees the current state of those files as a separate part. When a change cannot be shown whole, the next agent is told so. An agent reads whole files: a plain read of any text file shows the file from its first line, up to 2000 lines, and not a summary, and tells the agent where the next read continues. Every agent gets the same tools and the same instructions about how to work, and only its own brief differs. An agent that must not change files says so in its brief. A workflow can run an agent as a persona, such as a reviewer: that agent gets everything that a subagent of that persona gets, its instructions, its required skills, its tool limits, its turn limit, and its model, and the brief still states its task and its output. A workflow file that still names the tools of an agent, or marks an agent as one that only checks work, still runs, and the person is told that those keys no longer do anything. A workflow file in the grammar from before phases still runs: Flywheel reads it as phases, warns that the form is retired, and a run that the earlier form started resumes after an upgrade.

While Workflows is Ask or On, a chat agent writes a workflow for its task and launches it by content or path. Flywheel offers no launch by name. The agent passes the workflow's text in the launch call, and Flywheel saves it as a file in the session's scratch workflow folder, named by the workflow's id and replacing an earlier file of that name, and launches that file, so one call saves and launches it. The file holds the whole workflow, with its agents' briefs and declared outputs inline. A chat that lacks a tool that every agent gets cannot launch a file, and an agent can run as, or dispatch, only the personas that the chat can dispatch. The agent knows the full location of that folder, so it can edit a saved file and launch it again by its location. The agent can also launch a workflow file that it finds elsewhere, such as one in the project, by its location: Flywheel saves a copy in the session's scratch workflow folder and launches the copy, so the agent never reads a file only to pass its text. Before it writes a file, the agent can load a workflow authoring reference. The reference teaches only the phases, joins, repeats, and limits that the installed Flywheel runs, with examples that launch as written, and loading it launches nothing. A file that cannot run starts nothing: a file that is not valid, that asks for more than the chat has, or whose workflow is too large for the input that the launch passes. The file stays saved, and the refusal names it. The agent then learns every independent problem that the launch found, each with the file by its place in the session's folder, the phase, agent, or repeat, and the key that it names, and the refusal tells the agent to load the authoring reference before it fixes the file. Anything else that the launch finds, such as a part of the workflow that the launch cannot check from the file or a key that no longer does anything, does not stop the file: the workflow starts, and the launch tells the agent each warning on one short line, located as a problem is, and only the agent reads them: the parent chat's workflow card shows no launch warning. The card shows no launch line. The launch also tells the agent the model and effort that each agent starts on and the persona that each agent runs as. A list that a phase runs over, or that a join merges or ranks, needs no stated length or key: a list that the launch passes is as long as the agent made it, a list that an agent writes holds at most 100 items unless the file states another limit, and the launch says so, and each item without a key is known by its place in the list. In Ask mode, each launch needs the person's approval. The person approves the file as the question showed it, and an edit after the question needs a new approval. A stored approval for a retired named workflow cannot approve a file. The run keeps the workflow it started with: it resumes after the file is deleted, edited, or after a restart, and continues the same agents. Launching an edited file starts a new run. While Workflows is Off, no workflow can launch. Past runs of named workflows remain viewable. Resume, Restart, and messages refuse those runs and name the retired workflow.

Agents that do not wait on each other run at the same time. When several of them send the model the same brief and tools through a provider that can store a prompt for all of them, such as the agents of one phase over a list, the first one starts at once and each other one starts when the first has received its first reply, or after 5 seconds at the latest. The provider then stores the prompt that they share once, and each later agent reads it from that store instead of paying to store it again. Through a Claude subscription, the agents share only the tools and the project-wide instructions, and each agent stores its own brief. Every agent sends the same tools and project-wide instructions, also an agent that runs as a persona, so agents of different phases share that stored part too. Through a provider that keeps a separate store for each conversation, such as the OpenAI API or ChatGPT, the agents start together, because no agent can read the store of another agent.

An agent fails when it still fails after the retries that its workflow states, or when it stops three times in a row without its handoff after two reminders to write it; a message from the person or another session, or a Resume, starts that count over. An agent of a phase over a list that fails fails only its item: the other items run, and the join names the failed item. Any other agent that fails fails its phase. The other agents of that phase run to their end, the later phases do not run, and the run fails, because the parent reads the output of the last phase. Inside a repeat, a failed phase also ends the repeat. A phase whose condition does not hold is skipped, not failed, and the phases after it still run. The completion result names each failed agent with its reason, and the card shows the agent as failed, so a failed agent is never read as finished work. When a repeat stops at its round bound, or as stuck because a round found the same work as the round before, the workflow still completes, and its completion result and notification name each such stop beside the verdict, so a partial result never reads as full. The completion result also gives the parent each agent's result in the order of the workflow, labelled by its phase or agent id and, in a phase over a list, its item: the handoff of each agent that finished, with each command that the agent recorded and its result, the output of each join, and each agent that failed, was skipped, or did not run as such. The results share one size limit, which the latest results take first: the last agent reads and condenses the earlier ones, so its result reaches the parent even when the agents before it would fill the limit. The completion names each result that did not fit and how to read it, so the parent does not have to look up what the agents already returned. A run that fails this way tells its parent at once and stays resumable: a Resume from the person or from the parent runs the failed agents again, with the agents that wait on them, and every agent that finished keeps its result and does not run again. A run whose phases all ran but that still has a failed item agent ends as failed in the same way. A Resume then runs that item agent again with its later item phases, folds its list's join again, and runs again in full each later phase that reads that join, including a phase over a list or a repeat whose agents read it: such a phase runs again over what it reads now, so a new finding gets its own check and reaches the report. Every finished agent that does not read a failed agent's output keeps its result. The completion result says that a Resume runs the failed agents again. Each client offers that Resume where it offers the Resume of an interrupted run, and the failed run takes no message. A completed run, and a run that failed because its workflow could not add or expand work within its limits, cannot resume. An agent runs with nobody at the keyboard, so it recovers from provider faults on its own and never asks the person to act. When no provider can serve the agent until a stated time, such as a usage-limit reset, the agent waits and continues as every agent does (PI-MODEL-039). Its notice offers no button and stays until that agent's wait ends, while other agents of the run work or wait. A fault that only a person can fix, such as a rejected request, an unconfigured model, or a content refusal that cannot be repaired, ends the agent at once, and a context overflow ends it as PI-AGENT-010 states. A fault that can clear never ends an agent at its first occurrence. An agent whose model stream stalls, whose connection drops, whose provider stays overloaded or fails without a stated cause, or whose engine stops, continues from its recorded conversation on a fresh attempt, after a pause that grows with each attempt. Each served model request starts that count over. The agent fails only when the fault repeats on six fresh attempts in a row with no served request between them. While its model's access is still being checked, the agent waits for the check to end. When an account refuses its login, the agent waits for the login as an interactive run does (PI-MODEL-027). A subagent and a headless task recover in the same way.

## PI-AGENT-030: Headless chat uses standard input and output

Headless chat behaves like interactive chat, with standard input and output replacing the graphical or terminal client. It uses the same instructions, tools, conversation history, child agents, workflow supervision, authentication profile, and provider admission and failover. A versioned JSONL channel accepts messages, question answers or cancellations, interrupts, and stops, and streams responses and state changes. A question remains a question until the caller answers or cancels it; headless never invents approval.

An open input stream permits more conversation turns. In one-shot mode, the agent's final reply is its result, as in interactive chat, and the agent writes that answer once. A turn that ends while work the agent owns still runs waits for that work. A turn that ends with no owned work running completes the invocation, which flushes its evidence and returns the final reply without requiring input to close or an exit command. When input closes, submitted work can finish. In either mode, a question that still needs an answer produces an explicit input-required outcome, not approval or success. The session remains available for resume. Direct task automation remains supported. The headless workflow command refuses and names its replacements: headless chat, whose agent writes and launches workflows, and a direct task. Any changed invocation or output contract has an explicit migration.

A caller can inspect resolved settings without making a model request. Run evidence identifies actual provider attempts and child activity and distinguishes estimated equivalent value, billed cost, and unavailable accounting. Headless adds no provider filter, billing ceiling, or usage-percentage pause to the profile's normal policy.

## PI-AGENT-031: Chat orchestrates substantive work with workflows

While Workflows is On, the root chat agent delegates every substantive task. It aims for the most complete and correct result, not the cheapest one, and reaches it as soon as possible. It writes a workflow file for the task and launches it by content or path. It uses a workflow only when at least two agents are needed and a later agent reads an earlier agent's output. It gives one agent's work to a subagent and independent work to parallel subagents. Work in several parts, such as understand, design, and implement, runs as separate dispatches in sequence, and the chat reads each result before it starts the next part. A part holds all of its own agents: build, review, repair, and the verification of the repair run as one workflow, and its result is a first draft that the chat revises against the Design intent. Independent units of work start at the same time. A unit waits only for a named prerequisite or for a file that a running unit changes, and the order in which units commit does not make a unit wait. It prefers workflows that verify findings adversarially, unless the work is trivial or already verified. It works without delegation only on conversational turns and trivial mechanical edits. While Workflows is Ask, the agent launches only when its judgment says the task needs a workflow, and each launch needs the person's approval. While Workflows is Off, no workflow can launch, and the chat works directly or through subagents.

## PI-AGENT-032: Tool calls are read for what they mean

Flywheel carries out a tool call whose meaning is clear even when its form is wrong, such as a value in the wrong type or encoding, a misspelled key or option, a wrapped argument object, or a path that identifies exactly one existing file in another form. The result begins with a note that states how Flywheel read the call. Flywheel never changes a value that is already valid, never invents missing content, never chooses between two possible meanings, and never relaxes a safety, permission, or containment check; it refuses such a call with what the agent needs to correct it.

## PI-AGENT-033: Every finished background task reaches its parent

When a subagent, workflow, or background command ends, its result always reaches the conversation of the agent that started it, including after contention, a restart, a planned replacement, or a stop, and while that agent is mid-turn or waiting. Until it arrives, it counts as that agent's outstanding work.

## PI-AGENT-034: Each model request is inspectable

For any session, a person can inspect each model request: which context sources it used, what each one contributed, or its identity when the content was not kept, what was left out, cut short, summarized, compacted, or withheld and why, and which request, agent, or subagent produced later work. Inspection says which evidence it shows exactly and names each part that was not kept, instead of presenting a guess as exact. Each retry and each fallback to another provider appears as its own request.

## PI-AGENT-035: Subagent results are condensed and cited

A subagent takes bounded, noisy work off its parent, such as locating definitions, tracing a flow, inspecting logs, reviewing, summarizing a large artifact, or running an isolated experiment. Its parent receives a condensed result rather than every intermediate message, and the result cites the evidence needed to recover detail, such as file paths with line numbers, artifact or event IDs, URLs, or session IDs. A result larger than the parent's share of its remaining context is cut to fit; the parent reads which parts were cut and where the full result is kept, and the subagent row still shows the first sentence of its summary.

## PI-AGENT-036: Outcomes explain themselves

When Flywheel reports autonomous work as done, blocked, failed, superseded, or overridden, it shows a concise explanation of why that outcome follows from the work's target and evidence, linked to that evidence, so the person never reads raw history to learn why. The explanation can compress evidence, but it always names each criterion that is missing, failed, superseded, or overridden, and who overrode it.

## PI-AGENT-037: Instruction files stack from global to the working directory

Every agent turn follows the person's global instruction file first and then the repository's instruction files from the repository root down to the working directory, and the more specific file takes precedence. Each section names where it came from. A file that an instruction file names with @ is included as its own section, and a linked instruction file is read when its target stays inside the project or the person's home and outside Flywheel's own data. Edits to memory and instruction files take effect at the person's next message in a chat, and when a workflow agent or subagent starts. A subagent follows the instruction files from the repository root down to its own working directory. Instruction files below the working directory do not load, and an agent reads the governing file before it changes files there.

## PI-AGENT-038: Skills are for agents and commands are for people

Skills are methods that agents load. A person never runs a skill directly: no command list, palette, completion, or typed slash token offers one. Every action a person starts is a slash command, and a command that needs a method starts it as the chat's next turn.

## PI-AGENT-039: Learning has project or global scope

Every memory entry and learned skill applies either to the current project or to all of the user's projects. Learning that agents save on their own applies to the project unless it clearly concerns the user everywhere, and a background learning review may end without saving anything. A background review never changes a global skill; it recommends a promotion that the user decides. Promoting a skill moves it to global scope, so it no longer exists as a separate project skill.

## PI-AGENT-040: Learned skills never duplicate or change built-in skills

A skill that Flywheel learns on its own is saved only when an independent check finds that it neither duplicates nor contradicts a built-in skill, or that it correctly narrows one; when the check fails or is unclear, nothing is saved. Learned project skills that conflict with built-in skills are archived recoverably, and unclear cases are kept. Learning never changes or suggests changes to built-in skills. An installed skill with the same name as a built-in skill is used instead of it, and the built-in skill stays unchanged.

## PI-AGENT-041: A spent workflow budget pauses before the next attempt

A workflow's configured budget limits its attempts, tokens, and wall-clock time since launch for the whole run; its token limit counts the workflow's own agents and auxiliary usage, not the subagents those agents dispatch, and a chat has no workflow budget. The token limit counts the tokens providers reported. A request served without a usage report adds none, and the pause reason names how many such requests the run made. Flywheel checks the budget only before an attempt starts: a limit never stops an agent that is already running, the running agents finish, and the next start is refused, which pauses the workflow. A Resume of a paused workflow whose budget is spent is refused before anything continues.

## PI-AGENT-042: Repeated restarts without progress pause a workflow

After a host crash or restart, each running agent of a workflow continues in its conversation. An agent that crashes again after three restarts without progress is not restarted a fourth time: the workflow pauses. Any recorded progress starts the count over.

## PI-AGENT-043: Workflow verification checks without running

`flywheel workflow verify` checks a workflow file or a past run with the same rules that launch and execution use, and reports proved, partially proved, or invalid, with its uncertainties and the examples that prove each result. It never runs an agent and writes nothing. For a past run, it prints every phase, agent, and join of the run, with each join's kept and dropped entries and the records that the run left out of agent context with their reasons. When the run's history cannot be read back, it prints the reason instead of a guessed structure.

## PI-AGENT-044: Subagents nest at most three deep

An agent can dispatch subagents that dispatch their own. A chain of subagents is at most three deep below the chat or workflow agent that started it; a deeper dispatch is refused with the reason. A dispatch is never refused for its rate or count, but subagents beyond the running limit wait in a queue and start in dispatch order. Persona grants decide which child types an agent can dispatch. On trial since 2026-11-01, every agent of a workflow can also dispatch the advisor without a grant, except an agent that itself runs as the advisor.

## PI-AGENT-045: Large unused session scratch is reclaimed

Each session's scratch folder is disposable. Flywheel removes a top-level scratch entry larger than 100 MB after three days without a write, and removes a linked Git worktree there through its repository, so the repository no longer lists it.

## PI-AGENT-046: Agents work without per-call approval

Flywheel never asks the person to approve an individual tool call or command; the one exception is workflow launch approval while Workflows is Ask (PI-AGENT-031). Flywheel's command guards prevent ordinary mistakes but do not confine the programs that an agent runs (PI-AGENT-017). A person who needs confinement runs Flywheel inside a boundary such as a virtual machine, a container, a low-privilege account, or a disposable checkout.

## PI-AGENT-047: Processes that outlive Flywheel need explicit permission

Agent commands that keep running after Flywheel exits are off by default. A person turns them on in the configuration or for one launch with a command-line flag, and an agent must then ask for survival on each background command that it starts. While Flywheel runs, the agent can list such a process, read its output, and stop it. After Flywheel exits, the process keeps running and Flywheel can no longer list, read, or stop it. A command that is declared to change files cannot also keep running after Flywheel exits.

## PI-AGENT-048: Agent commands find the person's own programs

On macOS and Linux, an agent's shell commands find the same programs as the person's login shell, including the search programs that Flywheel bounds, whether Flywheel started from a terminal or as a background service. Until Flywheel knows the login shell's PATH, or when it cannot read it, commands use Flywheel's own PATH. On Windows, commands use Flywheel's own PATH.

## PI-AGENT-053: Agent searches stop when they grow too broad

An agent's search and list tool calls stop after 30 seconds of processor time, or after 120 seconds spent waiting on reads, and tell the agent to narrow the search. On macOS and Linux, the `grep`, `egrep`, `fgrep`, `rg`, `find`, `fd`, and `du` programs that an agent's shell command starts stop after 30 seconds of processor time with the same advice, except a `find` or `fd` call that runs a command for each result. These searches skip artifact directories such as `node_modules`, `.git`, and the project state directory, and every directory that the repository's ignore rules exclude, unless the call names one of them; `du` skips nothing. A depth-first `find`, such as one with `-depth` or `-delete`, still walks those directories but never reports or deletes anything inside them. The shell programs otherwise keep their own arguments, matching, and output.

## PI-AGENT-049: Agent file changes keep what they did not change

A file change by an agent tool keeps every byte it did not change: text decodes as strict UTF-8, an existing byte-order mark stays, existing line endings stay exact, and a new line ending follows the replaced line ending, then the nearest local style, then the file style. An update, overwrite, or move keeps the file's existing permissions without widening them, and a project file or directory that a tool creates gets the permissions that the person's own tools would give it.

## PI-AGENT-050: Skills install by link

A person can install a skill by linking its directory into a skill folder. The linked skill loads under the link's name and follows every edit to its source. Flywheel never changes the source through the link.

## PI-AGENT-051: Installed skills keep their own descriptions

Installed skills keep their own descriptions. A skill that a person installs from outside Flywheel reaches agents with its whole description as its author wrote it. Flywheel never shortens it. A person makes the skill list smaller by uninstalling skills.

## PI-AGENT-052: Commands that need more processor time than the machine has wait their turn

When agent commands need more processor time than the machine has, Flywheel runs as many of them at full speed as its processor budget serves and holds the rest, so commands finish one after another instead of all slowing together. The budget is the machine's logical core count of Flywheel's own commands' threads that are ready to run, and other programs on the machine do not reduce it. A held command resumes oldest first when the budget frees. A command that rarely has work ready to run never waits. A command that a chat's own turn starts is never held, and its demand counts toward the budget. A held command shows that it waits for processor time and keeps its output, and the time that it waits does not count against its timeout. When a held command reaches the foreground limit, the agent learns that it waits for processor time and how many commands are ahead of it.
