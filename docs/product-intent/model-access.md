# Model Access Product Intent

This document states the current intended experience for authentication, authorization, provider configuration, model eligibility, selection, routing, and failover.

## PI-MODEL-001: Invisible automatic provider failover

Automatic provider failover is invisible while an eligible, authorized fallback exists. Flywheel tries candidates in the defined resolution order within the same logical turn and tool call, without user action or a failure notice. The resolution order is by spend class: included subscription use first, then prepaid balance, automatic subscription spend, direct API spend, and aggregator spend; inside a class, by provider rank, then, for included subscription use of a provider whose accounts reset their usage windows at different times, such as Claude, by the soonest known reset of the window whose quota expires, and then account order. An account with no known future reset follows the accounts with one. This puts included quota that expires sooner to use first, even when a chat must leave the account it was using. A candidate is passed over only when it cannot serve the request for its own reasons: its quota or credits are spent, it is rate limiting, it is overloaded, it is unreachable, or its account does not grant the model or the model's extended context window. A free-plan account is never a candidate while its profile holds another account of the same provider. Those failures do not prevent trying authorized later spend classes. A failure the request itself caused, such as a rejected or malformed request, bad credentials, or an error the provider did not classify, would repeat on every candidate; Flywheel reports it at once under its own name and never describes it as spent quota or credits. Flywheel preserves completed work and attributes usage and cost to each provider attempt. It reports a terminal quota failure only after every candidate has failed on that class or is ineligible. When a candidate drops the connection, throttles, or reports overload, Flywheel retries that candidate in place with bounded backoff, shows the reconnect progress in the session status while it waits, and moves to the next candidate only when those retries are spent. A lost connection alone never marks a provider unreachable for other sessions; only a failure the provider stated does, and a first mark holds briefly and lengthens only while the outage persists. An agent that finds every candidate spent until a stated time, a chat included, waits for that time and continues on its own (PI-MODEL-039).

## PI-MODEL-002: Background process model visibility

Background process lists prioritize the full, wrapped goal and show the current resolved model and reasoning effort for each process that has one. Internal process identifiers are not displayed.

## PI-MODEL-003: Actionable unsafe account storage

When unsafe account storage blocks model access, Flywheel identifies the affected provider and storage path, marks that provider as needing attention in Authentication, raises one actionable provider-specific notification, stops retrying affected candidates until the credential store changes, preserves completed work, and lets the session retry after storage is repaired. When the file cannot identify an affected provider, Flywheel reports the authentication file itself.

## PI-MODEL-005: Subscription usage threshold crossings

Flywheel notifies once on an observed crossing from below each configured subscription usage threshold. A first observation already at or above the threshold is silent. A threshold becomes eligible again only after observed usage falls below it. Notifications identify the subscription and relevant usage window, use whole-number percentages, and include days until reset when known.

## PI-MODEL-006: Banked subscription usage resets

Usage lists every available banked reset with its expiration, earliest first. A single reset is one line; multiple resets form a vertical bulleted list. One Apply action reviews the earliest-expiring reset. Whenever a banked reset is available, the user can review and confirm its application from the Usage view. The provider decides at redemption whether a limit resets, and Flywheel reports that outcome and refreshes usage after it. In an interactive client, when no provider can serve a request and an account refused for used-up included usage has a banked reset, the refusal says so and names Usage as the place to apply it.

## PI-MODEL-004: Consolidated model identity

Equivalent provider spellings and stable provider route variants of one model appear and persist as one dotted model choice, while each provider receives the exact identifier for the selected eligible route. A dash between numbers becomes a dot only when a version follows it, so claude-opus-4-5 appears as claude-opus-4.5 while a parameter size stays apart from the version, as in qwen3-8b and llama-3.3-70b-instruct. A model pinned in flywheel.toml, or chosen in an account's model preferences, under a spelling an earlier release used keeps working and is rewritten to the current identity once the catalog names that model: a dotted parameter size, or a provider wire that now belongs to another model. Terminal compact and hyphenated date snapshots coalesce under the undated canonical identity; an undated provider wire wins, otherwise the newest dated wire wins. A stable provider model remains available when its own provider describes nothing about it, as long as another source prices it and states that it calls tools on text. Moving provider aliases are not model identities. A provider whose wire identifiers move between model snapshots, such as DeepSeek and OpenCode Go, names each model by the snapshot models.dev records for its wire, and by the wire itself when models.dev records none. A provider's free wire, such as an OpenCode Go identifier that ends in -free, is a free route of its model when the provider also serves that model on a paid wire, and an account uses it only when free routes are on; otherwise the free wire is the model's own route and serves the model without free routes. Flywheel is an agentic coding harness, so a provider route is listed only when it can serve that work: it has a known price for tiering, it calls tools, and it takes and returns text. Batch-only routes, image, audio, and embedding models, and models no source prices are never shown. User-authored custom provider models are the exception and are always listed.

## PI-MODEL-013: Profile-scoped training-route consent

Contributor routes are ineligible unless the active auth profile explicitly allows providers to train on requests sent through those routes. No other profile or account-wide value fills in for this permission, and a change applies from the next model request.

## PI-MODEL-017: Account-scoped OpenRouter free routes

OpenRouter free routes are off by default. For an exact OpenRouter account that includes them, Flywheel shows free variants under the same model choices, prefers an eligible free route, and retains that account's paid route as fallback. This preference does not grant contributor or training-route permission.

## PI-MODEL-014: Automatic session naming resumes after access recovery

When a recoverable authentication or provider-configuration condition blocks automatic session naming, Flywheel keeps the immediate quick title and retries naming after that environment refreshes, without delaying chat work.

## PI-MODEL-007: Consistent provider request identity

Provider requests identify Flywheel consistently wherever the provider permits application attribution, while required provider compatibility identities remain intact.

## PI-MODEL-008: Model assignment inheritance indicator

Model assignment lists show only the `↳` glyph when the effective model and effort both match the inherited pair, and show no indicator when either value differs.

## PI-MODEL-009: Provider controls target exact accounts

Arrow-key navigation in the authentication list keeps the selected row visible. Revealing the first row of a section or provider group also reveals the headings immediately above it when they fit with the row. The selected row takes priority when the viewport cannot fit both.

Provider and account rows open Provider Settings. Subscription model controls apply to the exact account being edited. Extra billing is account status, not a model-selection target. New credentials replace rejected credential data rather than preserving its rejection. Account settings distinguish usage status from model access and recommend recovery actions for the reported condition.

## PI-MODEL-012: Complete searchable provider catalogs

Model preference controls do not require a successful provider API call. When provider discovery fails, users can still view and edit the available saved or models.dev catalog. Catalog visibility and preference editing are independent of permission to send model requests. In model controls, an account whose model discovery has not yet run shows as still being discovered, never as failed or unavailable.

For SuperGrok subscriptions and Google Vertex accounts, usable coding candidates from models.dev appear immediately as editable preferences while background checks confirm which models that exact account can serve. Pending candidates are unchecked unless the user selects them; the profile's auto-enable default applies only after access is verified. Only a completed successful check makes that exact account's model eligible for requests. An explicit current access refusal hides the option; an inconclusive check stays pending and does not erase a prior success. Exact-account results survive restart and token refresh. When models.dev adds candidates, Flywheel checks the new IDs and previously successful IDs, not prior refusals; an explicit manual recheck retries access that may have changed. SuperGrok checks use subscription usage, and Vertex checks are not billed. Neither changes paid-use permission.

A provider's refusal of one model, or of only its extended context window, applies to that model and account alone. Flywheel does not retry the refused request on that account, mark the provider unreachable, or mark the account's quota spent, so the person's other models and accounts stay usable. The request moves to the next candidate, which can be another account that grants the model. When a provider states that the account cannot use a model, that model leaves the exact account's model controls and request routing. When a provider refuses only the extended context window, the exact account then offers the model at the standard window, and the next message uses that window and compacts the session first when it does not fit. When the provider refuses before it sends any part of the response, Flywheel sends the same request again once at the standard window instead. When no candidate can serve the request, the notice names the refused model or window, not a rate limit, and offers /model. The saved refusal applies to the exact model the provider refused, survives restart and token refresh, and ends after 24 hours, because the person can change what the account grants without a new credential. A new credential for the account starts without it.

Every provider's model controls show every usable stable model in the latest valid catalog Flywheel has saved for the same account, without waiting for the network, and replace it in the background when fresh discovery succeeds. Models offered through multiple providers appear under one stable shared identity while each provider retains its exact route. A missing cross-catalog relationship never hides an otherwise listable provider model. Outside SuperGrok and Google Vertex, the same saved evidence makes enabled models immediately eligible for requests. With no saved first-party catalog, Flywheel discovers the current catalog normally; when first-party discovery is unavailable or unusable, it uses models.dev as that exact provider account's catalog source, never as an independent provider or model-picker section. A failed refresh keeps the last valid catalog. An authentication rejection removes that account generation's saved catalog and stops admitting it, but model preferences remain visible and editable from models.dev for the configured account. Editing preferences does not authorize requests from an account whose authentication is rejected. Models are sorted from newest release to oldest using models.dev metadata, and users can search the complete list or deselect all models for the exact account. New models default to enabled under one policy for the active authentication profile and every provider account in it; changing that policy preserves current selections and every explicit account-scoped deselection. Flywheel does not maintain, hardcode, or curate provider model membership, and this behavior adds no prompt. Outside provider controls, only models checked for a current exact account enter model selection and request routing.

## PI-MODEL-010: Usage reads the same way on every client

Selecting a visible account keeps the account list's scroll position unchanged.

While Usage is open, tracked activity updates automatically as model requests are recorded, without losing the selected account, range, or scroll position.

Anthropic subscription account headlines show the weekly usage window. The five-hour window remains visible in the account details.

Each account's Flywheel activity separately reports the current local calendar month and each current account-wide provider usage window, with explicit date ranges. All-tracked activity remains available in Spend. Missing or partial accounting is explicit. An unknown price is flagged on its account and model and adds no money. A period reads incomplete only while accounting is still settling. An unavailable ledger reads unavailable, never zero.

Spend shows reported cache reuse, token breakdowns, and measured model-request counts over the selected range, overall and by account and model, separately from billed spend and subscription-equivalent value. A request that a provider served without reporting its usage counts as unmeasured, and a request whose report ended early counts as partially measured. Both are shown beside the measured count. An unmeasured request adds no tokens or money; a partially measured request adds the lower bounds it reported.

Usage is one view with Accounts, Spend, and History a tap apart, and a line beside that switch says when the reading is from, that it is refreshing, or that it failed. Each account is one row: its name, one reading of what is left or the reason there is none, and beneath it the plan, the signed-in identity, and whether paid use is allowed; no internal account id appears. Every account starts closed; a tap opens one at a time, and a tap on the open one closes it, showing its provider allowance as one bar per window with its reading and when it resets, its banked reset with the action to apply it, and what Flywheel did in the window. ChatGPT per-model windows stay hidden until asked for. Spend reads over a chosen range as totals and then each source with its models; History offers every account, metered keys included. For a subscription it charts each window the provider still reports and that saw use in the range, use rising as the window fills and dropping where the provider reset it, each reset marked once while the marks can be told apart, with the latest and peak readings beside the window's name; billed spend beyond the plan charts beneath when there was any. For a metered key it charts spend climbing through the range to its total. A Claude usage-only enterprise account reads as a metered account: no provider allowance and no usage windows, only what Flywheel tracked and billed.

## PI-MODEL-015: Model picker shows effort and price in place

The model picker shows each eligible model with the reasoning effort levels it supports and the effort that will apply. The user can adjust that effort in place before confirming model and effort together. Effort belongs to the selected role, not to the model: changing one role never changes another role's effort. Each model option uses the selected role's effort, adjusted to the levels that model supports. The picker shows the highlighted model's input, cached input, and output prices per million tokens with its position on the price range of the listed models. A model offered through several providers shows one price and one effort set: each value comes from the first provider in selection order that states it, then from models.dev, so a provider that lists only model identifiers still shows the price and efforts another source states for the same model. When the person confirms a model that the profile cannot use at that moment, Flywheel keeps the choice, and the confirmation names the model and effort that serve until the chosen model is usable, or says that no model can serve now.

The model picker names a model's eligible providers in first-appearance resolution order for the active authentication profile, each provider once regardless of how many accounts or billing routes it offers, joined by arrows. The provider that would serve the model at the moment the picker reads its models stands out from the others; when no provider can serve the model then, none does. The terminal shows the highlighted model's providers by their full names beneath its price details with the label "Providers:", such as `Providers: ChatGPT Subscription → OpenAI API Key`. The web client shows them in each model's row as one line under its name, by each provider's short name: the providers up to and including the one that would serve, then a count of the providers after it, such as `ChatGPT +1`; when none can serve, every provider. The picker never names a model's API format.

Opening model selection or provider model controls shows saved choices immediately and requests background discovery at most once per authentication profile every five minutes, including failed attempts. Concurrent openings share the same discovery, and no periodic polling is required. Fresh results update the open view in place without blinking, clearing usable rows, or remounting unchanged rows. The highlighted model, supported pending effort, search text, and scroll position stay stable. Ordinary background discovery shows no loading transition or success toast while usable choices remain.

## PI-MODEL-016: Every agent role has an eligible default

For every request, Flywheel resolves the role against the active auth profile's reachable models. It uses the role's saved model and effort when reachable, then its coded OpenAI preference, then its coded Anthropic preference, then the newest reachable model in its price tier. An unreachable saved pair is skipped, and the agent's transcript shows one system message that names the saved model and the model and effort that serve instead. The transcript shows another such message only when the serving selection changes or the saved model serves again, and the model never reads these messages. An unsupported effort maps to the nearest supported effort. When the tier is empty, Flywheel uses the nearest populated tier, or a reachable unranked model when no ranked model is reachable. A request and its resulting tool calls keep one selection; the next request resolves again. A profile whose model access is still being checked waits on discovery before selection, and a profile with nothing reachable shows the existing authentication or no-provider guidance.

## PI-MODEL-011: Paid-provider admission uses provider evidence

Flywheel skips a paid provider candidate before dispatch only when current provider-owned balance and pricing evidence proves the request unaffordable under that provider's billing rules. Unknown affordability remains the provider's decision, and another eligible candidate can serve.

## PI-MODEL-018: Paid use is asked once and never blocks

Connecting a subscription account whose provider reports paid capacity ends with one paid-use question that names the account, explains that paid use stays off until allowed, and offers each paid mode as a choice. Closing the question records that paid use stays off, so it does not return. Paid capacity detected outside a connection flow raises the same question once at the next safe moment, closable the same way, and it never blocks other work. The terminal never asks while the session on screen runs a model turn. The editor and phone show a notice that a paid-use question waits and never interrupt work. Provider Settings remains the place to change the answer later. Each auth profile keeps a separate answer for each account and each paid mode, with prepaid and automatic billing kept apart. A different profile or account starts with paid use off and unanswered, and a token refresh keeps the answer. Flywheel offers no profile-wide spend limit, billing toggle, or purchase path. An allowed paid mode works like an API key: after the account's included usage is gone, Flywheel sends requests through it, and the provider decides whether to serve them. Usage readings are shown for tracking and never block an allowed paid mode.

Automated terminal checks can explicitly suppress automatic account setup and paid-use questions without changing authentication, paid-use permissions, or recorded answers. Manual account controls remain available.

## PI-MODEL-019: Session title model selection

People can choose the model and reasoning effort used for automatic session titles in the Background section of model configuration. Each title request uses the current setting of the session's auth profile. An unreachable saved model and its effort are skipped together. Without a reachable saved choice, titles prefer GPT-6 Luna at low effort, then Claude Haiku 5.5 at low effort. When neither is available, titles use the newest reachable cheap model at low effort. Only when that tier is empty do they use the nearest populated tier, or an unranked model when no ranked model is reachable.

## PI-MODEL-020: Current subagent model visibility

Linked subagent cards and child viewers show the model and reasoning effort that serve the child now, and update when either changes. A model or effort change in a child viewer applies only to that child, at its next request. An unreachable or unsupported setting falls back to the defaults, and settings never refuse a subagent dispatch.

## PI-MODEL-021: Model selection applies at each request

An agent uses the current effective model, reasoning effort, and provider options at each request boundary. That selection stays fixed for the request and its resulting tool calls, not for the runner's lifetime. A selection change applies to the next request without replacing the runner, losing conversation state, or interrupting background work. A change to a model of another provider, or between the Claude engine and another route, also while the agent waits on the results of its tool calls, continues the same conversation and shows no warning: the agent reads its earlier replies, progress updates, and tool work as its own, but never the earlier model's private reasoning, so that reasoning cannot appear as something the agent said. General agents inherit the selection of the parent request that starts them.

## PI-MODEL-022: Prefilled SuperGrok sign-in

SuperGrok sign-in opens a verification link with the device code included, without asking the user to copy or enter it.

## PI-MODEL-023: Auth profiles remain available and deletion transfers sessions

Flywheel always provides at least one auth profile. Creating, renaming, or deleting a profile updates already-open clients without a restart.

Deleting an auth profile transfers its affected saved sessions and workflows before removing it. When one other profile remains, the confirmation names that profile as the automatic destination. When several remain, the person chooses a destination in the confirmation. Deleting the last profile creates a fresh Default with no credentials or profile-specific settings inherited from the deleted profile, then transfers the sessions and workflows to it.

## PI-MODEL-024: Provider-scoped prompt-cache retention

People can configure prompt-cache retention separately for each API provider that supports a retention control, without changing subscription policies. An omitted value preserves the current default. A configured policy applies at the next provider request, including a fallback request, while an explicitly uncached request stays uncached. A provider refusal identifies a selected model that cannot serve the requested policy. A provider-managed policy does not promise a fixed cache lifetime.

## PI-MODEL-025: Accounts of the earlier native Anthropic Subscription provider move to the Anthropic Subscription provider

Flywheel has no provider that runs the Claude sign-in itself. Claude subscriptions reach Flywheel only through a Claude login that the Claude engine that ships with Flywheel holds for one Flywheel profile (PI-MODEL-027).

When a person installs a release, each Claude account that the earlier native Anthropic Subscription provider stored moves to the Anthropic Subscription provider in the same profile. Flywheel finds the same account by its Claude account id, or by its email address when the stored account has no id. The account's saved model choices and paid-use decisions move with it, so they apply again when the person logs in to that account. Flywheel then deletes the stored Claude sign-in tokens. It never uses them for anything else, and it never writes them to a log.

The person must log in to each moved account once from Authentication, because a profile never uses a Claude login that the person made outside Flywheel. This is the one approved exception to the rule that an update never asks for a new login. The person does not reselect a model. Until the login, the Anthropic Subscription row shows its Log in button, not an error. Flywheel shows one notice for each profile that names each account that needs a login and tells the person to log in to it from Authentication. The log gets one warning for each account, with its email address.

A stored request to turn on the earlier opt-in provider modules needs no repair. Flywheel reads it as the default selection and removes it from the configuration file.

## PI-MODEL-026: Terminal API-key entry shows a character count

When a person enters an API key at a terminal prompt, the terminal never shows the key. The question prints once on its own line and stays whole. While they type or paste, the row under it shows only the number of characters received, and the count follows the line-editing keys, a window resize, and a return from the background. The count row is plain text that never wraps in a usable terminal. When they press Enter, Flywheel confirms the key with the same hint that the stored-key status shows: the last 4 characters behind a mask, or "!command" for a command reference. A cancel leaves no key text on screen. Piped input gets no count and no confirmation. The key never reaches a log, an error message, or the prompt's input history.

## PI-MODEL-027: Claude through a Claude login for each profile

The Anthropic Subscription provider serves Claude models through the Claude engine that ships with Flywheel: the engine program that the Claude Agent SDK pins, in every release for every platform. Every surface that names the provider, such as Authentication, Settings, Doctor, notices, and `flywheel auth`, calls it Anthropic Subscription. The engine runs and keeps the Claude sign-in. Flywheel never reads, stores, or sends the Claude sign-in token. To show and route each account, it reads only the account details that the engine records, such as the email address. The provider works in the same way whether or not the person has a separate install of the engine, and it never uses such an install. A request at reasoning effort off uses the model's own off mode, as on the Anthropic API-key provider.

Each Claude login belongs to one Flywheel profile, as every other credential does. The login button of a profile runs the engine's own login into a folder of that profile. A new profile has no Claude account, even when the person is signed in to Claude elsewhere on the computer, and a login in one profile does not appear automatically in another. When the same Claude account is logged in to two profiles, each profile has its own login, and Disconnect in one profile leaves the other profile logged in. Disconnect logs the account out of that profile only: a separate install of the engine and every other app keep their own logins. Flywheel never reads, uses, or changes a Claude login that it did not create. A profile in a separate Flywheel home of the same computer account can use a Claude login of a profile in the account's own Flywheel home by reference; both use that one login, and Disconnect in the separate home removes only the reference.

The provider is on by default. Its Settings row is an ordinary provider row with no risk confirmation, and turning it off and on again asks nothing. Nothing needs to be installed for it. The engine never updates itself and never downloads anything; a new engine comes only with a new Flywheel release.

The engine that Flywheel runs and a separate install of the engine that the person runs never interact. Flywheel's engine reads and writes no setting, login, hook, instruction file, cache, log, data folder, editor connection, temporary file, or socket that belongs to the person's install or to the project's Claude configuration. It keeps each of these for a login in a folder of that login, and the person's install finds nothing of Flywheel's engine. Neither one sees or signals the other's processes. The machine's Claude policy, which an administrator sets for every Claude install on the machine, applies to both.

Each account row shows the account's email address and, when the engine names it, its plan. When the engine cannot read an account's login and sends no request, Flywheel starts a fresh engine and sends the same request once more, and the person sees nothing. When Claude refuses an account's login, or a fresh engine also cannot read it, the row says so and one notice says the same.

In each open project, every interactive run and every agent of a workflow or subagent that needs that account waits, and every client asks once for that account's login condition: "Log in again?" The question and the waiting runs belong to that project. The question names the account and profile and says that this project's runs wait and that declining ends them. Yes starts that account's existing login. When the login succeeds for the same account, the waiting runs continue with the exact request that failed. No, closing the question, a failed or cancelled login, or a login to a different account ends the waiting runs with their original login error.

Flywheel does not retry their requests under a different account. Later runs that meet the same refusal end with the login error without another question until a successful login or a served request clears the condition. Stop ends a waiting run at once without ending other runs that wait for the account. A login in one project continues another project's waiting runs only once that project's question is answered or its next request on that account is served. Headless tasks and stdin/stdout chat fail immediately with the login error instead of waiting or asking.

When the engine exits while it serves a request, the row and one notice say so; Flywheel starts it again for the next request. When the engine cannot start on this machine, because it is missing, is not executable, or is built for another C library, the request goes to the next route at once, and the row and one notice say that the engine cannot start and how to repair the installation. A request that the account then serves clears the row and the notice. In every client, a browser login shows the sign-in page and a field for the code that the page shows.

`/doctor` reports where the engine is, the version that the engine states, and each account with its plan and its status. For each account it also names the account's login folder, where the engine keeps the token, and how the account's last request in this process ended. A login folder that serves no account says what it holds. `/doctor` never reads a token or a credential file. An engine that does not run asks the person to reinstall Flywheel, and a Linux login without a token asks the person to log in again.

When enabled and eligible, this provider is the first provider route for Claude models. This priority preserves account availability checks, included-capacity ordering, and paid-use consent.

Claude usage-only enterprise accounts use their account's normal metered billing without a paid-use question. For accounts with included usage, extra usage stays off until the person allows it for that account (PI-MODEL-018), and Flywheel asks the paid-use question when the engine records that extra usage can bill it. While paid use is off, Flywheel stops using an account as soon as the engine reports that the account served a request from extra usage, or does not show that included usage served the request. The answer that the account already returned is kept. Flywheel holds the account until its included usage resets, or for a few minutes when the engine reports no reset, so the next requests go to the next route. One notice names the account, says that it used extra usage and that Flywheel stopped it, and says where to allow paid use in Provider Settings.

This provider preserves Flywheel's tool capabilities, tool execution, and the user's message text. Provider-specific tool names remain a transport presentation.

This provider and the Anthropic API-key provider give the model reminders with the same facts. At the start of each conversation context, the reminders state the working directory, git state, platform, shell, operating-system version, the model's name and knowledge cutoff, and today's local date. After later user input, a reminder states a change in the working directory, git state, model, or local date, and the request after a tool round states a change in the model or the local date. On every route, the environment block of the system prompt states the local date on which the turn started, so the prompt changes at most once a day, at a turn boundary. The local date is the same on every route and agrees with the date that the Claude engine states. On macOS and Linux it is the date in Flywheel's time zone, which `TZ` sets, and the engine gets that zone. On Windows it is the date in the Windows system zone, whatever `TZ` names, because the engine on Windows dates in the system zone and ignores `TZ`; Flywheel gives the engine no `TZ` there. Reminders are ordinary system-origin conversation entries: they are saved in model history but hidden from the visible transcript, survive resume and forks, reset with the active context, and remain in history when the user switches providers. On a Claude login the engine also gives the model the account's email address. That text is not in Flywheel's history, and the Anthropic API-key provider never sends it. An agent that runs in a shared Claude engine also receives text that the engine writes: an identity line, fixed agent instructions, the environment, model, and date, and a coordinator line each time it resumes. Flywheel records each of these as a system-origin entry in that agent's history, hidden from the visible transcript. On Windows with Git for Windows installed, the engine states the shell as bash, where the shared reminders state PowerShell. The person accepts that line. Each request that the engine sends states the environment once, also after a rotation and at each dispatch of a hosted agent, so the model never reads two shell lines. The description of Flywheel's shell tool states that commands run in PowerShell on Windows, and that description is the authority.

## PI-MODEL-028: A workflow file can set each agent's model

Each request from an agent of a workflow resolves its model and effort from the authored settings of its session and the current settings of the run's auth profile. The narrowest saved session setting wins as a whole before the profile's persona or Workflow Agent setting, then the coded role preferences and tier. A setting that names only an effort keeps the default model. The launching chat never chooses an agent's model. The default picker does not list briefs, and a defaults-scope save to a brief refuses with guidance to set the Workflow Agent default or the agent's session setting. Saved profile brief settings remain intact, but never apply, and Flywheel warns about them. A running agent's picker saves only its unfixed fields to that workflow session. The Workflow Agent picker saves to the profile.

A workflow file launched by content or path can fix the model, effort, or both for one record. The run keeps only those authored fields; unset fields follow current profile policy, also after Resume. An unreachable saved model and its effort are skipped together. An independently fixed effort remains in force when the model falls through, and unsupported effort maps to the nearest supported effort. Model availability and unsupported effort never refuse a launch. The launch reports its current selection, or that no model is reachable or access is still being checked. The workflow and agent views show current effective selections. Workflow card rows show each agent's current effective selection, and an agent-view edit updates its row at once. The picker marks authored fixed fields and changes only unfixed fields. A workflow-wide model change reaches only fields that the file did not fix, and only sessions that still inherit that choice. An agent-view edit changes that session alone. Resume and recovery keep its local choice. A fresh retry or round uses the workflow's current choice. Resetting the workflow clears its session overrides, keeps authored fixed fields, and resolves again; it does not remove an agent session's local override. Choosing inheritance in that session removes only its override. The Workflow Agent has no Inherit row. Session settings saved under earlier brief names and profile settings saved under earlier Workflow Agent names keep their meaning without action from the person.

## PI-MODEL-029: An agent can list the models its session can use

An agent can list the models its session can use now, with each model's provider, release date, knowledge cutoff, prices, supported efforts, and tier role. For first-party provider models released in the last six months, the list also gives Flywheel's quality, speed, and cost tiers from 1 to 10 for each effort, which Flywheel computes from public benchmark data that it fetches when an agent first asks and refreshes at most once a day. A new model can gain tiers without a Flywheel update. The list never shows raw benchmark scores. The list reflects the active profile's enabled models and access at each call. Asking for the list never changes the cached prompt prefix.

## PI-MODEL-030: The Benchmark Judge setting is listed only with development tools

The model settings list the Benchmark Judge role only while the development module is on. A model set for that role stays saved while the module is off or absent, and applies again when it is back on.

## PI-MODEL-031: A refusal of conversation content does not end the run

When a provider refuses a request because of content in the conversation, Flywheel withholds that content from the model, tells the model what it withheld and why, shows the person the same note in the transcript, and continues. This repeats while each refusal names content that Flywheel has not yet withheld. When Flywheel cannot find the refused content, it removes the most recent tool calls and their results, tells the model not to run them again, and tries once more. If the provider still refuses, the run ends with the provider's error. What Flywheel withheld or removed stays withheld for every later request on every provider, and resuming a session that already holds refused content recovers the same way.

## PI-MODEL-032: The environment and the project select the auth profile

Flywheel uses the auth profile that `FLYWHEEL_AUTH_PROFILE` names, by exact ID or else by a unique case-insensitive display name; otherwise the profile bound to the current project; otherwise the last profile the person chose; otherwise Default. A profile named by the environment applies to that process only and never changes a saved choice; while the environment names the profile, that process cannot switch to another profile or delete the named one. A project's profile binding is private to the person's account and is never stored in the project.

## PI-MODEL-033: A session keeps the auth profile it uses

Each session keeps the auth profile it started with until the person switches that session to another profile. Changing the default profile, or launching with a different profile in the environment, does not change a saved session's profile or its model roles. Switching a session's profile applies that profile's models to the session at once. Work already in progress finishes with the profile, credentials, and model access it started with.

## PI-MODEL-034: Sign-in from any client signs in the machine that runs the runtime

Signing in, disconnecting, or renaming an account from any client changes the accounts of the runtime that the client is attached to, never those of the device the person holds. A terminal on the runtime's own machine opens each sign-in page on that machine, so a sign-in that returns to the machine finishes without pasting a code. A terminal or phone attached through the relay shows the sign-in address to open in the person's own browser. For a sign-in that returns to the machine, it also takes the code or the final address that the page ends on; for a device-code sign-in, it shows the code that the person enters on the provider's page.

## PI-MODEL-035: An API key for another provider is refused

When a person enters an API key for a provider whose own keys carry a known prefix, and the key visibly carries another installed provider's prefix, Flywheel refuses the key and names the provider that the key belongs to. A key with no known prefix is accepted, and a provider whose keys carry no known prefix accepts any key.

## PI-MODEL-036: Custom OpenAI-compatible providers come from configuration

A person can declare a custom OpenAI-compatible chat-completions provider in flywheel.toml with its endpoint, its complete model list, and an optional models.dev identity. The entry's presence turns the provider on, with no module toggle or Settings row. The person adds its API key in Authentication, where the provider appears under the entry's id. An edit to the file reaches Authentication and new sessions without a restart; a session that is already open keeps the providers it started with. An entry that fails a semantic check, such as an invalid id or a non-HTTP address, stays visible in Authentication as misconfigured, with the reason, so the person can fix it.

## PI-MODEL-037: The automatic sign-in dialog never interrupts another dialog

When no provider is set up, the terminal opens Authentication on its own once each time it starts, and only when no other dialog is open. It checks again first and does not open when a provider was set up meanwhile. A message sent while no provider is set up is not sent: the terminal says why and opens Authentication. Authentication opened by hand always shows a fresh view.

## PI-MODEL-038: Free-plan accounts never rotate

Only paid subscription accounts rotate. A profile holds at most one free-plan account of a provider, and a free-plan account serves only while it is the only account of its provider in the profile. Flywheel reads each account's plan from its provider: a ChatGPT account on the Free plan and a GitHub Copilot account on Copilot Free are free-plan accounts. An account whose provider reports no plan counts as paid. SuperGrok accounts and Claude subscriptions always count as paid.

When a person signs in to a free-plan account and the profile already holds an account of that provider, Flywheel refuses the account, stores nothing, and says why. When Flywheel cannot read the new account's plan and the profile already holds an account of that provider, it refuses the account the same way and says to try again later. When a person signs in to a paid account and the profile holds a free-plan account of that provider, Flywheel asks before it stores anything: "This will replace your attached free subscription because we only allow multiple copies of paid subscriptions." Confirming stores the paid account and disconnects every free-plan account of that provider. Declining stores nothing. Every client and the `flywheel auth login` command follow these rules.

A free-plan account that sits beside another account of its provider, because its paid plan lapsed or because it was connected before this rule, stays connected and does not serve. Its account row says why and offers to disconnect it, and Flywheel tells the person once. It serves again as soon as it is the only account of its provider or its plan becomes paid again.

## PI-MODEL-039: Every agent waits out spent capacity and continues

When no candidate can serve an agent until a stated time, such as a usage-limit reset, the agent waits until that time and then continues its turn on its own, with no action from the person. This holds for every agent: a chat, a workflow agent, a subagent, and a headless task. A spent candidate that states no time is checked again after a short interval, so a wait never turns into a failure while every candidate can still clear. When the time comes, the agent's next request decides: if a candidate serves it, the turn continues from where it stopped; if every candidate is still spent, the agent waits again for the next stated time. The wait of an agent that the runtime serves continues across a runtime restart, an unexpected exit, and a reboot, and whether or not a client shows the session. A headless task waits while its own process runs, and ends with that process. A project that closed during the wait opens again when the agent continues. A machine that sleeps through the time continues when it wakes. While it waits, every client shows "Waiting for model capacity" with the agent's name and the time it continues, also after a restart. An interrupt or a Stop ends the wait, a message from the person starts a turn at once, and a headless task's own deadline ends its wait. A wait never admits a paid candidate that the person did not allow, never applies a banked reset, and pages no one.
